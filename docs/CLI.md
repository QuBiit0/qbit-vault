# CLI reference

`gentle-vault [global flags] <command> [flags]`

Global flags: `--home <dir>` (default `$GENTLE_VAULT_HOME` or `~/.gentle-vault`), `--json` (machine output, exactly one JSON object on stdout), `--session <id>` (host session; required by `exec`, `set --grant`, `grant`, `revoke --session-only`), `--quiet`, `--no-color`.

Values are **never** accepted as arguments. `set` and `import` read from the masked prompt or stdin.

**Layers.** Every secret is either `global` or belongs to the project (repository) of the current directory. Commands that take `NAME` act on the record that `NAME` resolves to from the current directory (project first, then global); `--global` or `--project` picks a layer explicitly. `--project` outside a repository fails with `no_project` (exit 3).

## Setup

| Command | What it does |
| --- | --- |
| `version [--json]` | Print version, commit and platform. Human: `gentle-vault <version> (<commit>, <os>/<arch>)`. JSON: `{"ok":true,"version":…,"commit":…,"go":…,"os":…,"arch":…}`. |
| `init [--agents claude-code,codex,opencode,pi,gentle-shell] [--no-extension] [--passphrase] [--passphrase-stdin]` | Full one-shot setup. See INSTALL.md. Idempotent. **Until slice 3.6 `init` is vault-only**: it creates the master key and an empty vault and nothing else (no host registration; `--agents` and `--no-extension` do not exist yet). `--passphrase` keeps the key in `key.enc` instead of the OS keychain. Without `--passphrase-stdin` the passphrase is asked twice on the controlling terminal (`/dev/tty`, `CONIN$`; input hidden, never read from stdin); a mismatch is the usage error `passphrases do not match`, Ctrl-C or end of input is `cancelled` (exit 1), a blank one is `empty passphrase`, and none of them creates anything. With no controlling terminal it is the usage error `no controlling terminal available; use --passphrase-stdin`. `--passphrase-stdin` reads the first line of stdin instead. If the vault already exists it exits 0 and reports `initialized: false`. If creating the vault fails, the key just created is removed. |
| `sync` | Re-apply host registrations from `state.json` receipts (after upgrades). Not vault sync: that is `remote` (below). |
| `doctor [--json]` | Read-only health report. Exit 0 healthy, 1 warnings, 2 errors. |
| `uninstall [--purge]` | Revert every host change from snapshots, remove the extension. `--purge` also deletes the vault after the user types `purge`. |
| `update [--check]` | Download, verify (Minisign + checksums) and replace the binary. Opt-out of the background check with `config.update_check: false`. |

## Secrets

| Command | What it does |
| --- | --- |
| `set NAME [--global\|--project] [--stdin] [--description D] [--sensitive] [--binaries gh,git] [--hosts api.github.com] [--grant once\|session\|project] [--reason R]` | Store or replace a value. Without `--stdin` it is interactive: inside a repository with neither layer flag it first asks *global or this project (label)* (default global), then shows the request (name, reason `manual entry`, host, session, layer, whether the value is new or already stored) and reads the value from the controlling terminal with echo off (`/dev/tty`, `CONIN$`; never from stdin; nothing is echoed, not even a mask). The terminal takes **one line**: a multi-line paste is refused with the usage error `the input continued after Enter; paste a single line, or use --stdin for multi-line values`, the extra text is discarded from the terminal input queue (flushed, so the shell never sees it and it never reaches history) and nothing is stored; multi-line values need `--stdin`. The same applies to passphrases. Blank input is the usage error `empty value`, input over 64 KiB `value too large`, Ctrl-C or end of input at any question is `cancelled`; an unanswered prompt gives up after the **prompt timeout** (below) with `prompt timed out`, also exit 1 and code `cancelled` (exit 1, stderr `error: cancelled`); none of them writes anything. With no controlling terminal it is the usage error `no controlling terminal available; use --stdin`. Interactive `--grant once\|session\|project` is the proposed scope: after the value a menu offers the scopes this secret and session allow (`once` only for a sensitive one, `project` only on a project secret, `once` and `session` only with `--session`) plus `no grant (store the value only)`, and choosing one is the confirmation (the grant is audited as `prompt token`); a grant that cannot be made is refused before the value is asked. `--from-prompt-token` is `--stdin` only (usage error `--from-prompt-token needs --stdin`). `--stdin`: read value from stdin (used by hosts). `--grant` also creates a grant for `--session` in the same call (used by the capture flow so first use costs one prompt); because stdin carries the value there is no question to ask, so `--grant` **requires `--from-prompt-token T`** (usage error `--grant requires --from-prompt-token`; `--from-prompt-token` alone is `--from-prompt-token requires --grant`), and the token is checked, and the scope validated (a `sensitive` secret accepts `once` only), **before** anything is stored: a refused grant stores nothing. Replacing the value of an existing secret drops that record's grants (R-API-07). With `--stdin` there is no layer question: inside a repository pass `--global` or `--project`, else usage error `choose --global or --project`; outside one, `set` writes to the global layer. Surrounding whitespace is trimmed, the trimmed value is at most 64 KiB, and a blank value is a usage error (`empty value`) that writes nothing. Replacing a secret keeps the metadata you do not pass again. |
| `rm NAME [--global\|--project] [--yes]` | Delete value and all its grants. Without a layer flag it deletes the record `NAME` resolves to. Without `--yes` it asks `Remove NAME (<layer>)? [y/N]` on the controlling terminal; anything but `y`/`yes`, Ctrl-C or end of input is `cancelled` (exit 1) and removes nothing. With no controlling terminal it is the usage error `confirmation required; pass --yes`. `--yes` never asks (for scripts). |
| `mv NAME --to global\|project [--yes]` | Move a secret between global and the current project. Keeps value and metadata, drops its grants, asks before overwriting a same-named secret in the target: `NAME already exists in <layer>; overwrite? [y/N]` on the controlling terminal (a no or cancel is `cancelled`, exit 1, and nothing moves), or, with no controlling terminal, the usage error `NAME already exists in <layer>; pass --yes to overwrite`. `--yes` overwrites without asking. Outside a repository it fails with `no_project`. |
| `list [--layer here\|global\|project\|all] [--json]` | Names and metadata, never values. `here` (default): what resolves from this directory, marking project overrides. `global`: only the global layer. `project`: only this repository's layer (`no_project` outside one). `all`: every layer including other projects. Human output is a table `NAME  LAYER  DESCRIPTION` (`LAYER` is `global` or `project:<label>`; overrides are marked `(overrides global)`); an empty result prints `no secrets`. While sync conflicts exist (REMOTE_SYNC § 7.4) the human output also prints `N sync conflicts; run 'gentle-vault remote conflicts'` on stderr; stdout and `--json` are unchanged. |
| `describe NAME [--global\|--project]` | Metadata, layer and active grants for one secret. `grants` lists the active grants of that record only (a grant on the global `NAME` is not shown on the project `NAME`): `{"scope","session","expires_at"}` each; human output shows `none` or `<scope>, for <session>, until <time>` (`until revoked` for `project`). |
| `edit NAME [--global\|--project] [--description] [--sensitive=true\|false] [--binaries] [--hosts]` | Change metadata, never the value. At least one change flag is required (usage error otherwise). Making a secret `sensitive` drops its `session` and `project` grants (a `once` grant stays) in the same operation; the JSON then carries `grants_dropped`. Other edits keep their grants. |
| `link LABEL [DIR]` | Bind a project layer that has no root on this device (it came from another machine through sync) to the repository root of `DIR` (default the current directory). User-only: confirmed through the prompt backend (`Use the secrets of project <label> in <root>?`), never automatic, and with no prompt backend it is refused with `not_model_callable`; a no is `cancelled`. `DIR` outside a repository is `no_project`. Errors never echo `LABEL`: `no unlinked project layer has that label`, `several unlinked project layers have that label`, `this repository already has a project layer`, `give the label of the project layer to link`. Grants are not carried (there are none on this device yet). Audited as `link`. Human: `linked <label> to <root> (N secrets)`. `list --layer all` marks such layers `(not linked on this device)` (`"unlinked":true` in JSON), and a human `list` in a repository whose origin matches one prints `hint: project secrets "<label>" from another device match this repository; run 'gentle-vault link <label>'` on stderr. |
| `relink OLD_ROOT NEW_ROOT` | Repoint a project layer after moving or re-cloning a repository. `OLD_ROOT` must be an existing project layer (it need not exist on disk); `NEW_ROOT` must be a repository root (contains `.git`, else `no_project`) without a layer of its own. **Grants do not follow the layer:** every grant of the old project layer is dropped (relink can only narrow access) and the user grants again for the new root; the output reports `grants_dropped`. |
| `import --from-env NAME[,NAME…]` / `import --from-file PATH [--names A,B]` `[--global\|--project] [--yes] [--remove-source]` | Explicit, user-run import from the current environment or a dotenv file. Never run by `init`. Prints what it imported by name and offers to unset/remove the source. Give exactly one source (`choose --from-env or --from-file`); `--names` and `--remove-source` need `--from-file`. Layer as for `set`: the flag, else global outside a repository, else the question `Where should these secrets live?` (no prompt backend: `choose --global or --project`). Unless `--yes` it asks `Import A, B from <the environment\|the dotenv file> into <layer>? Existing secrets with these names are replaced.` (no prompt backend: `confirmation required; pass --yes`; a no is `cancelled`). Every value is trimmed like `set`, at most 64 KiB (`NAME is too large`), and all are stored in one locked write: a replaced secret keeps its metadata and loses its grants. Environment: a missing or empty variable is `NAME is not set or empty in the environment`; afterwards stderr says `hint: unset A B in your shell; gentle-vault cannot change the environment of the shell that started it`. Dotenv (at most 1 MiB, else `dotenv file too large`; unreadable: `cannot read the dotenv file`): `KEY=VALUE` lines, `#` comments, optional `export `, single quotes literal, double quotes with `\n \r \t \" \\` escapes, both may span lines, unquoted values end at a ` #` comment; a line with no `=`, an invalid name or an empty value is skipped and counted (`note: skipped N lines (invalid name, no '=', or empty value)` on stderr); a syntax error is `the dotenv file has an error at line N: unterminated quote` (or `text after the closing quote`), never quoting the file; the last of repeated names wins; a `--names` entry the file lacks is `NAME is not set in the file`; nothing left is `nothing to import`. `--remove-source` deletes the file afterwards; interactively the user is asked `Delete the dotenv file now that its values are in the vault?`. Audited as `capture` with `reason` `import from env` or `import from file`. Human: `imported N secrets into <layer>: A, B` plus ` (replaced: B)`. |
| `rekey` | Rotate the master key, crash-safe (STORAGE.md § Master key): the new key is staged first (keychain account `master:next:<id>`, or `key.next.enc` under the same passphrase), then `vault.enc` (snapshotted), `grants.enc` and `keys/retired.enc` are re-sealed with it and the old key is retired, then the new key replaces the old one. In passphrase mode the passphrase is asked to wrap the new key and must be the current one (a wrong one is `vault_locked`, exit 4, and nothing changes); changing the passphrase is not part of `rekey`. A rolled-back or corrupt vault is refused (`vault_corrupt`) before anything changes. If the process dies midway, the next command that opens the vault finishes the rekey and prints `warning: an interrupted rekey was finished` (audit `warning`). Grants and backups survive (old backups open through the retired key). Audited as `rekey` with the keychain mode. Human: `master key rotated (keychain: <mode>)`. **With sync enabled** it is user-only (it shows the new recovery key out of band; with no prompt backend it is `not_model_callable`), asks one confirmation, and runs REMOTE_SYNC § 4.5 steps 3-6 without revoking anyone: one account-wide rotation to generation g+1, every device switches on its next round, the recovery key is replaced. Human: `master key rotated (keychain: <mode>); the account is now generation N`; `--json` gains `"remote":"synced"`. |
| `lock` / `unlock` | Passphrase mode: drop / refresh the cached master key. `lock` reads no key and asks nothing: in passphrase mode it deletes the unlock cache (`vault locked: the cached master key was removed`); in keychain mode there is nothing to drop (`nothing to lock: the master key is in the OS keychain (<mode>)`). `unlock` always asks the passphrase (it does not trust a cached key), checks that the key opens the vault and caches it where a memory-backed cache exists (`vault unlocked until <time>`); without one it says `passphrase ok; this platform has no unlock cache, so the passphrase is asked on each use`. In keychain mode it only checks the key (`unlocked: the master key is in the OS keychain (<mode>)`). A wrong passphrase is `vault_locked` (exit 4) and leaves the cache as it was; no prompt backend is the usage error `no controlling terminal available`. Neither writes an audit record. |
| `restore --list` / `restore --from ID [--yes]` | Restore the vault from an encrypted backup. Give exactly one of `--list` or `--from` (usage error `choose --list or --from`). `--list` needs no key: one line per snapshot, newest first, `<ID>  <files>` (`no backups` when there are none). `--from ID` takes an id from that list (anything else is `invalid backup id`, never echoed; a valid id with no snapshot is `no backup <ID>`), asks `Restore the vault from <ID>? The current vault is backed up first. [y/N]` unless `--yes` (no prompt backend: `confirmation required; pass --yes`; a no is `cancelled`), opens the snapshot's `vault.enc` with the current key or a retired one (`keys/retired.enc`), and saves it as the next write: the current pair is snapshotted first and the rollback counter moves forward. It works when the live vault is corrupt or rolled back, and unlocks with the snapshot's vault id when the live `state.json` is unreadable. A snapshot no known key opens is `vault_corrupt` (`backup cannot be opened with the current or a retired key`) and changes nothing. Grants are kept (they bind record ids, which restore keeps). Audited as `restore` with the backup id. Human: `restored the vault from <ID> (the previous state was backed up first)`. |

**Several values in one call (hosts; lands with roadmap slice 4.3, the Pi extension's capture, together with `prompt --field`; the MCP path does not need it, the broker stores multi-field captures itself).** `set --stdin --fields A,B,C [--kinds secret,text,text] --grant S --from-prompt-token T` reads one JSON object `{"A":"…","B":"…","C":"…"}` from stdin and stores every field in one locked operation, all-or-nothing (a missing, extra or blank field stores nothing), then creates one grant per record with a token issued for exactly those names. It is how a host stores the values of a multi-field capture (CONTRACT `request` with `fields`). `--kinds` defaults every field to `secret`.

## Remote sync

Opt-in multi-device sync through `gentle-vault-server` (`REMOTE_SYNC.md`). Commands marked *user-only* ask every question and show every code through the prompt backend (native dialog, else the controlling terminal), accept no code, key or invite as argument or on stdin, never print the recovery key or a confirmation code on stdout, stderr or `--json`, and are refused with `not_model_callable` when no prompt backend is available.

| Command | What it does |
| --- | --- |
| `remote register --server URL [--ca-file PATH]` | *User-only.* Register this vault on the server as the first device: asks the invite code, confirms, uploads the vault sealed on this device, then shows the recovery key and asks for its last four characters (a wrong answer shows the key again, up to 5 times). The device's state is saved before the key is shown, so cancelling there leaves the account registered and `remote status` warns `recovery key not confirmed`. `https://` only, except loopback `http://`; a refused invite is `remote_auth`. Needs an initialized vault and a prompt backend that can show text, else `not_model_callable`. |
| `remote join --server URL [--recovery] [--ca-file PATH]` | *User-only.* Add this machine. Default: pairing; prints the pairing code (`XXXX-XXXX-XXXX-XXXX`, safe to show) and waits up to 10 minutes for `remote approve` on another device, then asks the confirmation code shown there. `--recovery`: asks the recovery key instead. A non-empty local vault is merged into the account after a confirmation that names how many secrets will be added. Needs an initialized vault (`init` first): the account master key replaces the local one the way `rekey` does (the old key is retired). With `--json` the pairing code goes to stderr so stdout stays one object. A wrong confirmation code, an expired pairing or a code the server cannot vouch for is `pairing_failed` and leaves the vault as it was; an unknown recovery key is `remote_auth`. |
| `remote approve` | *User-only.* On a device that already syncs: asks the pairing code and a label for the new device, verifies the code against the new device's keys (`pairing_failed` when they do not fingerprint to it), confirms, then shows the confirmation code to type on the new device. Audited as `approved <device id>`. |
| `remote sync [--json]` | Run one sync round now (pull, merge, push). Prints `synced (version N)`, `up to date (version N)` or `pending: <reason>` (`--json`: `{"ok":true,"result":"synced\|up_to_date\|pending","version":N,"reason":"…"}`). With `GENTLE_VAULT_NO_REMOTE=1` it only marks the push pending. An unreachable server is `remote_unreachable` (exit 1) and marks the push pending; a version older than one already seen is `remote_rollback` (exit 5). A key generation newer than this device's first runs the key swap of REMOTE_SYNC § 4.5 (the new key is accepted only from a key envelope issued by a non-revoked device of this device's own roster, with a valid signature and AAD, that opens the server's current vault; otherwise `remote_auth`, `the new account key could not be verified`, and the device keeps its key); an older generation is `remote_rollback`. A round that finds a device this device did not know, added by pairing or recovery, appends an audit `warning` (`device added: <label> via pairing\|recovery`). A server that answers `device_revoked` turns sync off on this device (`remote/` and `state.json.remote` removed; vault, key and backups stay), prints `this device was revoked; sync is now off here and the local vault is intact` and exits 1 with code `device_revoked`; in the automatic rounds of other commands the same line is a `warning:` and the command still exits 0. |
| `remote status [--json]` | Server, account, device, generation, version, last sync, pending push, conflicts, devices, anchor state. Read-only: it never prompts and makes no network call (it reads `state.json` and the encrypted roster). Exits 1 with `warning:` lines on stderr (`warnings` in `--json`) when a push is pending, conflicts exist, the recovery key was never confirmed, or a device was added by recovery. `anchor` is the time (UTC, RFC 3339) of the last audit anchor this device uploaded (REMOTE_SYNC § 8), or `none uploaded`. |
| `remote devices [--json]` | The roster, read-only and offline: one line per device with id, label, `added:` (pairing, recovery, register), `last sync:` and `revoked:`; this device is marked. |
| `remote revoke-device ID` | *User-only.* Revoke a device and rotate the master key and the recovery key. Refused with a usage error, before any prompt, for this device (`this device cannot revoke itself; use 'gentle-vault remote logout'`), an id that is not in the roster, or one already revoked. Confirms out of band (label, last sync), pulls and merges, then one `POST /v1/rekey` (a 409 restarts from the pull, at most 3 tries, then `the server changed while rotating the key; try again` and nothing changes here), re-seals the local files with the new key through the staged `rekey` path, and shows the new recovery key with the last-four confirmation of `register` (cancelling that screen leaves the account rotated and `remote status` warning `recovery key not confirmed`). Audited as `remote` `device revoked <id>` and `rekey` `remote generation N`. Human: `revoked <label> (<id>); the account key is now generation N`; `--json`: `{"ok":true,"revoked":"<id>","generation":N}`. |
| `remote recovery-key --rotate` | *User-only.* Replace the recovery key; the old one stops working. The account key and the vault stay as they are (`PUT /v1/recovery` at the current generation); when the account key may also be exposed, run `rekey`, which replaces both. Shows the new key with the last-four confirmation, which clears `recovery key not confirmed`. Without `--rotate` it is a usage error. Audited as `remote` `recovery key rotated`. Human: `recovery key rotated`; `--json`: `{"ok":true,"rotated":true}`. |
| `remote conflicts [--json]` | Records whose other version was kept after a double edit: name, layer, when it lost, and the label of the device that won (from the roster; `unknown device` when it is not there). Read-only and offline: no prompt, no request, never a value, description or any other field of the record. Human: `NAME  global\|project:<label>  kept edit\|deletion lost at <time> to <device>`, or `no sync conflicts`. `--json`: `{"ok":true,"conflicts":[{"name","layer":"global\|project","project"?,"lost_at","winner","deleted"?}]}`, newest loss first. |
| `remote resolve NAME [--global\|--project] --keep current\|conflict` | *User-only.* `--keep current` keeps the record as it is and discards every kept version of it; `--keep conflict` swaps: the kept version becomes the record (fresh clock and record id, so no grant of the replaced record applies) and the replaced record becomes the kept version (a kept deletion deletes the record; run `--keep current` afterwards to end the conflict). Without a layer flag the name must have a kept version in exactly one layer. One confirmation out of band; the result is pushed like any change (`"remote"` in `--json`, which is `{"ok":true,"name","layer","keep","remote"?}`) and audited as `remote` `conflict resolved (keep X)` with the name. Fixed messages, none echoing the name: a name with no kept version is `no sync conflict for that name` (code `not_found`, exit 1); a name kept in several layers is the usage error `several layers hold a conflict for that name; choose --global or --project`; several kept versions of one record make `--keep conflict` the usage error `more than one version was kept for that name; use --keep current to discard them`; an unlinked project layer is `not_found`. `--keep` missing or other than `current`/`conflict` is a usage error; no prompt backend is `not_model_callable`; a cancel changes nothing. |
| `remote history [--json]` | The server's last 10 versions, newest first: version, label of the device that wrote it (from the roster; `unknown device` otherwise) and the time the server stored it. Read-only, needs the server (`remote_unreachable` otherwise), no prompt. Human: `N  <device>  <time>`; `--json`: `{"ok":true,"versions":[{"version","device","at"}]}`. |
| `remote restore --version N` | *User-only.* Make the records of the vault equal to those of server version N. It first runs a sync round (so records from other devices are replaced too), downloads version N and verifies its AEAD and AAD (this account, this generation, version N), then confirms out of band (version, writer, time) and writes the difference as **new** changes: a record that differs or is missing gets the stored content with a fresh clock and a fresh record id (so it wins over the current one everywhere and old grants do not apply), a record N lacks is removed and leaves a tombstone, an identical record is left alone. The device roster, the kept conflicts and the grants are not restored (a revoked device stays revoked). The replaced state stays in the local backups (the normal snapshot) and the result is pushed like an edit. Human: `restored version N (K records changed)`; `--json`: `{"ok":true,"restored":N,"changed":K,"remote":"synced\|pending"}`; audited as `remote` `restored version N`. `--version` missing, not a positive number: usage error; a version the server no longer keeps: `restore_unavailable` (`that version is not on the server; run 'gentle-vault remote history'`); a version sealed under an older account key (before a `rekey` or revocation) cannot be opened with the current key: `restore_unavailable` (`that version was sealed under an older account key and cannot be restored`); a blob that fails AEAD or AAD, or is not version N: `remote_auth` (`the requested version could not be verified`). All leave the vault unchanged. |
| `remote logout` | *User-only.* Stop syncing on this device; the local vault and key stay. |

With sync enabled, every command that changes the vault pushes afterwards (5 s budget) and commands that read it for a person or the agent pull first when the last pull is older than 60 s (2 s budget); `exec`, `grant`, `revoke`, `grants` and `audit` never use the network. A push that could not reach the server prints `warning: not synced (server unreachable); will retry` on stderr and the change stays committed locally (exit 0); `--json` success objects of `set`, `rm`, `edit`, `mv`, `relink`, `link`, `import` and `restore` gain `"remote":"synced"|"pending"`, only when the vault syncs (they are unchanged otherwise; the broker's `manage` response is pinned by the contract and has no such field). A round the server's answer makes unsafe (`remote_rollback`, a refused verification, a refused device) is never reported as an outage: the change stays local, the push stays pending, and stderr says `warning: not synced (<code>); the change is kept on this device; run 'gentle-vault remote status'`, also on a read; the command still exits 0. A failed pull before a read is silent when the server is unreachable. The 5 s push budget, the 2 s pull budget and the 60 s pull interval are fixed for now (no `config.yaml` loader yet). `rekey` with sync enabled rotates the account key (see its row). `audit --verify` also checks the server's anchors (`--offline` skips them; a new reason `anchor_mismatch`; see its row).

## Grants

| Command | What it does |
| --- | --- |
| `grant NAME [--global\|--project] --scope once\|session\|project [--ttl 30m] [--from-prompt-token T]` | Grant the record `NAME` resolves to (or the layer named by the flag) after an explicit confirmation. `once` and `session` need `--session` (usage error otherwise); `project` binds to the repository root of the record and needs no session. `--ttl` (session scope only, 1m to 24h, default 30m) is a usage error elsewhere or out of range. A `sensitive` secret accepts `once` only, and `project` scope on a global record has no project to bind to: both are refused as `scope_not_allowed` before any question is asked (the second with the message `project scope needs a project secret`). Confirmation (L5): with `--from-prompt-token` the token must be valid for exactly this name, layer, scope, session and TTL (an omitted `--ttl` means the 30m default, so `--ttl 30m` and no `--ttl` are the same binding; a different `--ttl` is refused and burns the token), and for this record when the token was issued for one; otherwise the question `Grant NAME (<layer>) to <session or "this project">, scope <scope>? [y/N] ` is asked on the controlling terminal (L4; never on stdin, so a pipe cannot answer it); only `y` or `yes` (any case) confirms, anything else, Ctrl-C or end of input is `user_declined`. With no controlling terminal and no token: refusal `not_model_callable` (exit 3, audited as a refusal). The `grant` audit record is written **before** the grant is stored; if it cannot be written the grant is not created (refusal `internal`). A repeat grant replaces the identical one. Human: `granted NAME (<layer>): <scope>, for <session>, until <time>` (`until revoked` for `project`). |
| `revoke NAME [--global\|--project] \| --all \| --session-only` | Revoke grants; no confirmation (it only narrows access) and effective for the next check (R-GRANT-06). Give exactly one of `NAME`, `--all` or `--session-only` (usage error otherwise). `NAME` alone revokes it in every layer, with `--global`/`--project` in that layer only; `--all` also discards pending prompt tokens; `--session-only` revokes the grants of `--session` (project grants have no session and stay). Human: `revoked N grants`. The `revoke` audit record is best effort. |
| `grants [--json]` | Active grants (expired and used `once` grants are purged first): name, layer, scope, session, expiry and time remaining. Human output is a table `NAME  LAYER  SCOPE  SESSION  EXPIRES  REMAINING` (`-` where it does not apply), or `no active grants`. |

If `grants.enc` could not be trusted (corrupt, or older than recorded: a rollback) any command that touches grants prints `warning: grants were reset (store unreadable or rolled back)` on stderr, records an audit `warning` (`grants reset`), and carries on with no grants (`STORAGE.md` § Grants).

### Manual entry (no agent involved)

```
gentle-vault set GITHUB_TOKEN --global       # masked prompt, available everywhere
cd ~/code/shop-api
gentle-vault set DATABASE_URL                 # asks: global or this project (shop-api)?
gentle-vault list                             # GITHUB_TOKEN (global), DATABASE_URL (shop-api)
```

The same flow exists as `/vault set NAME` inside Pi / Gentle Shell. With Claude Code, Codex or OpenCode, run it in any other terminal. The terminal prompt reads the controlling terminal, not stdin, so a pipe cannot answer it; with a desktop session the prompt is a native dialog, not the terminal. When there is no controlling terminal (for example when launched by a host's shell escape without one) `set` fails with `no controlling terminal available; use --stdin`; on a machine with a desktop session the native dialog opens instead of the terminal (`AGENT_INTEGRATIONS.md` § Native capture dialog), so that case is rare.

## Exec

```
gentle-vault exec --session S --secret NAME[=ENV] [--secret …] [--timeout 10m] [--shell auto|sh|bash|cmd|pwsh] [--cwd DIR] [--stream] -- <command…>
```

- Each `--secret NAME` injects vault secret `NAME` as env var `NAME`; `--secret GH_TOKEN=GITHUB_TOKEN` injects `GITHUB_TOKEN`'s value as `GH_TOKEN`.
- `--stream`: stdout/stderr forwarded as redacted chunks as they arrive (NDJSON `{"stream":"stdout","chunk":"…"}` with `--json`, raw otherwise), final record carries `exit_code`.
- **Command.** The words after `--` are joined with single spaces and handed to the shell as one command string; they are not re-quoted. At most 16 `--secret` flags; `--timeout` between 1s and 1h; the command is 1 to 16384 bytes.
- **Shell.** `auto` is `/bin/sh -c` on POSIX; on Windows it is `bash -c` when `bash` is on PATH (Git Bash), else `cmd /d /s /c`. `sh`, `bash`, `cmd` and `pwsh` force one; an unavailable shell is a usage error.
- **Order of checks.** (1) resolve every secret from the working directory (`--cwd`, default the current one); (2) grants, looking only; (3) dump-command guard (`dump_command`) over the injected variable names; (4) binary allowlist over every pipeline segment (`scope_binary`); (5) hosts advisory (the audit record notes `hosts warning`, the run goes on); (6) consume `once` grants and append the `started` audit record, fail-closed; (7) run. Any refusal runs nothing.
- **Environment.** The child gets the parent environment minus every variable named like a vault secret (case-insensitive on Windows), plus the granted values. The parent is never modified. The child inherits stdin.
- **Output.** Human mode streams the child's redacted stdout/stderr to ours. `--json` prints one object `{"ok":true,"exit_code":N,"stdout":"…","stderr":"…","duration_ms":N,"redactions":N,"truncated":bool}`; each stream is capped at 1 MiB keeping the tail. `--json --stream` prints NDJSON: `{"stream":"stdout|stderr","chunk":"…"}` lines as output arrives, then a final `{"exit_code":N,"duration_ms":N,"redactions":N}`.
- **Timeout.** On expiry the whole process tree is killed (POSIX process group, Windows job object) and the refusal `timeout` (exit 3) is returned; with `--json` it carries `partial: {stdout, stderr}`, in human mode the partial stdout was already streamed. SIGINT/SIGTERM kill the tree and exit 130.
- **Wrapper flags and allowlists.** Wrappers (`sudo`, `env`, `timeout`, `nice`, `strace`, `xargs`, ...) are resolved with an explicit table of known flags. A flag outside the table, or a short-flag cluster whose letters are not all known, is ambiguous and the command is refused with `scope_binary` when an injected secret has a `binaries` list. Write such commands without the unusual flags, or call the program directly.
- **`--shell cmd` / `pwsh` and allowlists.** The dump guard and the binary allowlist split commands with POSIX grammar, which cmd.exe and PowerShell do not follow. So when the effective shell (after resolving `auto`) is cmd or pwsh and any injected secret has a non-empty `binaries` list, `exec` only accepts a single simple command: one containing none of the characters that shell can use to chain, start or substitute commands (cmd: `& | < > ^ % ! ( ) "` and line breaks; pwsh: `; & | < > ` + "`" + ` $ ( ) { } @ " '` and line breaks), whose first word, wrappers not resolved, is in every list. Anything else is refused with `scope_binary`. In those two shells the dump guard also tests the raw command, split at every separator and ignoring quotes, so it can refuse more than under `sh`/`bash`.
- **Exit code:** the child's. On POSIX a child killed by a signal exits `128+signal` (137 for SIGKILL); on Windows the code is whatever the OS reports. Refusals exit 3 with the typed refusal on stdout (`--json`) or stderr.

## Audit

| Command | What it does |
| --- | --- |
| `audit [--tail N] [--since 24h] [--name NAME] [--event exec] [--json]` | Read the log, oldest first, filters combined, `--tail` (default 50) applied last. `--since` takes a positive Go duration (`90m`, `24h`); `--event` one of the events in STORAGE.md § Audit log; `--name` a valid secret name; anything else is a usage error. Works without unlocking the vault. Human: one line per record, `<ts> <event> <names joined by ,> <layer> <session>` plus `exit=<code>` when present (`-` for empty names or layer); an empty result prints `no audit records`. JSON: `{"ok":true,"records":[…]}` (the records as stored). |
| `audit --verify [--json]` | Validate the hash chain; cannot be combined with the filters. Human: `audit log ok (N records)` (`1 record` for one), exit 0, or `audit log broken at line L (seq S): <reason>`, exit 1, both on stdout. JSON: `{"ok":true,"valid":true,"records":N}` or `{"ok":true,"valid":false,"records":N,"problem":{"line":L,"seq":S,"reason":"…"}}` with exit 1 (`records` counts the records that verified before the problem). Reasons: `bad_json`, `bad_hash`, `bad_prev`, `bad_seq`, `partial_line`, `truncated`, `head_mismatch`, and `anchor_mismatch`. With sync enabled and the chain valid, it also fetches this device's audit anchors from the server (REMOTE_SYNC § 8; 5 s budget; this is the only network use of `audit`) and checks the log against them: every anchored `seq` inside the log must match the hash of the raw line at that `seq`, else `anchor_mismatch` at that line (exit 1); a log with fewer records than the highest anchored `seq` is `truncated`. Human adds `remote anchor ok (seq N, <time>)`, `remote anchor: none uploaded` (the server holds no anchor this key opens and this device never uploaded one), `remote anchor: missing (this device uploaded anchors; the server returned none this key opens)` (after a key rotation, or a server that removed them; does not fail) or `remote anchor: unavailable` (server unreachable, a refused login, no way to unlock the key without a prompt; the verification does not fail); JSON adds `"anchor":"ok\|none\|missing\|unavailable"` (plus `anchor_seq` and `anchor_at` for `ok`). `--offline` (only with `--verify`, else a usage error) and `GENTLE_VAULT_NO_REMOTE=1` skip the check and add nothing to the output, as does a vault that does not sync. Anchors sealed under a key from before a rotation do not open and are ignored. |

Without a vault home both forms fail with `not_initialized` (exit 1). `init`, `set`, `rm`, `edit`, `mv`, `relink` and every typed refusal append a record; if that write fails the command still succeeds (or refuses) as before and prints `warning: audit log write failed` on stderr.

| Command | Used by |

| `mcp` | Hosts start it as a stdio MCP server. Env: `GENTLE_VAULT_SESSION` (optional). Exactly four tools, `secret_request`, `secret_list`, `secret_exec`, `secret_manage`, with CONTRACT.md's descriptions verbatim and the `policy` text as the server `instructions`. One prompt shows every field (stored ones marked *already stored*), one layer question and one scope menu; the token is bound to all the names. | `prompt --name NAME --reason R [--value] [--scopes once,session,project] [--layers global,project]` | The broker's own prompt, on the backend `GENTLE_VAULT_PROMPT` selects (a native dialog when a desktop session exists, else the controlling terminal; see `GENTLE_VAULT_PROMPT` below). It asks *which layer* (when `--layers` allows both and the working directory is in a repository; default the first listed), shows the request, with `--value` reads the value with echo off, then asks *which scope* (`--scopes` ∩ what the secret and `--session` allow; the last entry is `deny`). It issues a prompt token (2 minutes, single use) and prints `{"ok":true,"token":"…","scope":"…","layer":"…"}` (plus `"value_on_fd":3` with `--value`); the host redeems it with `grant --from-prompt-token` or `set --stdin --grant --from-prompt-token`. The command appends a `prompt` audit record (names, `layer`, `scope` when issued, `session`, `outcome` `issued`, `denied` or `cancelled`, best effort; never the value, the token or the reason), except when it refuses before asking about the secret (unknown secret, no scope possible). `--reason` is required and at most 1024 bytes; it is shown escaped (control characters and bidi marks become visible escapes). Used internally by `request` on non-Pi hosts. |
| `prompt --confirm --action remove\|edit\|move\|replace --name NAME --layer L --reason R [--diff JSON]` | Opens the native confirmation for a `manage` proposal; prints `{token, confirmed}`. |
| `broker --op <op>` | Raw contract call with the envelope on stdin; used by the Pi extension and by conformance tests. Reads one request (at most 64 KiB) and prints exactly one JSON object: the op's success payload or a typed refusal (CONTRACT.md); exit 0 on success, else the refusal's exit code (3, 4 or 5). `--op` must equal the envelope's `op` (else `invalid request: op`). A request that fails validation is `invalid_name`, `contract_mismatch`, or `internal` with `invalid request: <field>` (the field, never its value). `grant` needs `prompt_token` here too (`not_model_callable` without one). The capture is audited with `by: agent` and the request's reason. `manage` resolves the record in the named layer for `cwd` (`unknown_secret` otherwise), asks one confirmation `The agent proposes to <action>. Reason: <reason>. Apply?` (an edit lists `field: before -> after` and marks clearing `sensitive` or emptying an allowlist as `(widening)`; a move says when it overwrites the target), applies only on yes (`replace` then asks the new value, masked), never creates a grant, and on a no or cancel answers `user_declined` with the same cooldown as `request`. Audited as `manage` with `by: agent`, the action, the reason and `applied` or `declined`. |

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Success (for `exec`: child exited 0) |
| 1 | Generic failure / doctor warnings |
| 2 | Usage error / doctor errors |
| 3 | Typed refusal (see CONTRACT.md) |
| 4 | Vault locked |
| 5 | Vault corrupt / rollback detected (also `remote_rollback`) |
| N | `exec`: child's exit code when > 5 is ambiguous; `--json` always carries the real `exit_code` |

Typed refusals (exit 3, 4, 5) print the contract envelope `{"ok":false,"refusal":{"type":…,"name":…,"message":…,"retryable":…}}` on stdout with `--json`, and `error: <message>` on stderr otherwise. Operating on a home with no vault is not a refusal: it exits 1 with code `not_initialized` and message `no vault here; run 'gentle-vault init'`. A vault held by another process is the refusal `internal` with `retryable: true` and message `vault is busy` (until the contract has a dedicated type).

Failures that are not typed refusals (usage errors, `not_initialized`, internal errors, panics) never print free-form output in `--json` mode: stdout carries exactly one object `{"ok":false,"error":{"code":"usage"|"not_initialized"|"cancelled"|"internal","message":"…"}}` and nothing else. Without `--json`, stderr gets `error: <message>` (usage errors add `Run 'gentle-vault --help' for usage.`). A usage error includes an invalid `--session` (must match `^[a-z0-9-]+:[A-Za-z0-9._-]{4,128}$`) and running with `--json` but no command. `--help` is always human text with exit 0. The code `cancelled` (exit 1, message `cancelled`, or `prompt timed out` after the prompt timeout) is a user who gave up at a prompt: Ctrl-C, end of input, a no to a confirmation, or no answer in time; nothing was changed. Panics print only `internal error`, never the panic value.
