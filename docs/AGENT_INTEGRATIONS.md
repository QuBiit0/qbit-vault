# Agent integrations

One broker, one contract, three hosts: Claude Code, Codex and Pi / Gentle Shell. OpenCode was in the original design and is dropped (`odd/tasks/hosts.md` S8; no adapter exists). "Built" means `init` registers it and it is tested; *extension* items need the Pi extension `qbit-vault-pi` (Phase 4 v1, built; 0.2.0 adds the output and write guard; not on npm, `GENTLE_SHELL_EXTENSION.md`); *deferred* items are not built (not in v1 of the extension, or not on the roadmap yet for the other hosts). "MCP" is the portable path through `secret_exec`; today it is the path every host uses.

| Capability | Pi / Gentle Shell | Claude Code | Codex |
| --- | --- | --- | --- |

## MCP server (all hosts)

Started by the host as `qbit-vault mcp`. Exposes exactly four tools with the normative descriptions from `CONTRACT.md`, and the `policy` text as the server `instructions` returned at `initialize`, so hosts that surface MCP instructions give the agent its rules before any call. Input schemas are the `requestReq`, `listReq`, `execReq`, `manageReq` definitions minus the envelope fields, which the server fills in (`session` from `QBIT_VAULT_SESSION` or a generated `mcp:<uuid>`, `cwd` from the server's working directory, which hosts start in the project root).

The MCP server never exposes `grant`: there is no such tool, and a `grant` envelope sent over a model-facing transport (`broker --op`) is refused with `not_model_callable` unless it carries a prompt token the broker's own prompt backend issued.

### While a dialog is open

`secret_request` and `secret_manage` wait for the user, who answers in a dialog outside the chat. What the agent and the client see meanwhile:

- **Locked vault.** In passphrase mode with no unlock cache, every tool (`secret_list`, `secret_exec`, `secret_request` and `secret_manage`) first asks the passphrase in a dialog headed `Vault passphrase` that names the requester and the secret (`Claude Code wants to use GITHUB_TOKEN. Unlock the vault to continue.`), then go on to their own work: unlocking never grants, so `secret_exec` still needs its grant and `secret_request` and `secret_manage` still ask their permission question. `secret_list` has no name (`Claude Code needs the vault. Unlock it to continue.`) and `secret_exec` names the secrets it uses. The dialog is one of the serialized dialogs and ends with the call. A wrong passphrase answers the retryable `vault_locked`. A cancel answers `user_declined` for `secret_request` and `secret_manage` and the retryable `vault_locked` for `secret_exec` and `secret_list` (the user was asked; the message does not name a command). With no prompt backend, or with `QBIT_VAULT_NO_PROMPT_UNLOCK=1` in the server's environment, `secret_exec` and `secret_list` answer `vault_locked` with the message `vault is locked and no unlock dialog could be shown; ask the user to run 'qbit-vault unlock' in their terminal` (the one case that sends the user to a terminal), and `secret_request` and `secret_manage` answer `vault_locked` as before. The hooks never ask (below). The unlock is one `unlock` audit record naming the requester.
- **Progress.** If the client sent a progress token with the call, the server sends `notifications/progress` every 15 s until the call ends (a fixed text, never a name or a value), so clients that reset their request timeout on progress keep waiting. Without a token nothing is sent. The dialog itself still ends after `QBIT_VAULT_PROMPT_TIMEOUT` (5 minutes by default) with `user_declined`.
- **Cancel.** If the client cancels the call (`notifications/cancelled`), the dialog is closed (the native helper process is killed) and the call ends with a retryable `internal` refusal, "the request was cancelled before the user answered". Nothing is stored, granted or recorded in the audit log as a capture or grant, even if the user typed an answer at that moment, and no cooldown starts: it is not a decline.
- **List and exec agree.** `secret_list` shows a `grant` only when `secret_exec` would accept it from the same directory (the check is the same and a `once` grant is never spent by listing). A grant that exists but does not apply there (approved in another repository, or for an earlier value) is `"grant":null` with an optional `grant_note` that says to call `secret_request`; `secret_exec` refuses with `grant_required` and the same advice in its message (issue #42).
- **One dialog at a time.** The server shows one dialog at a time. A second call made meanwhile waits for the first dialog to close and then asks its own question; cancelling the waiting call ends its wait without ever showing a dialog. Calls that do not prompt (`secret_list`, `secret_exec`) never wait for it.
- **Quiet stderr.** The server writes nothing to stderr on these paths; a recovered panic leaves one fixed line.

The end-to-end driver `e2e/mcpclient` can exercise this: a `tools/call` step with `"progress": true` reports how many progress notifications arrived, and `"cancel_after": "2s"` cancels the call that long after it started.

### Registration written by `init`

**Claude Code** (adapter `claude-code`, `internal/hosts/claude`): four steps, each written into a user-scope file after a snapshot, owning only its own entries.

| Step | File | Owns |
| --- | --- | --- |
| `mcp` | `~/.claude.json` | `mcpServers.qbit-vault` |
| `hooks` | `~/.claude/settings.json` | the hook entries whose `statusMessage` starts with `qbit-vault hook ` |
| `deny` | `~/.claude/settings.json` | the two `permissions.deny` strings below |
| `skill` | `~/.claude/skills/qbit-vault/SKILL.md` | the whole file (§ Agent skill) |

Claude Code keeps **user-scoped MCP servers in `~/.claude.json`** (top-level `mcpServers`), not in `settings.json`; hooks and permissions live in `settings.json` (checked 2026-11-04 against <https://code.claude.com/docs/en/mcp.md> § MCP installation scopes and <https://code.claude.com/docs/en/settings.md>). Detection is read-only: `~/.claude` is a directory, or a `claude` binary is on `PATH`.

`~/.claude.json` (`command` is the absolute, symlink-resolved path of the running `qbit-vault`; `env` appears only when the vault home is not `~/.qbit-vault`):

```json
{ "mcpServers": { "qbit-vault": { "type": "stdio", "command": "/usr/local/bin/qbit-vault", "args": ["mcp"], "env": { "QBIT_VAULT_HOME": "/data/vault" } } } }
```

`~/.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse":  [
      { "matcher": "Bash|PowerShell", "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "pre-bash"], "timeout": 10, "statusMessage": "qbit-vault hook pre-bash" }] },
      { "matcher": "Write|Edit|MultiEdit|NotebookEdit", "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "pre-write"], "timeout": 30, "statusMessage": "qbit-vault hook pre-write" }] }
    ],
    "PostToolUse": [
      { "matcher": "Bash|PowerShell", "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "post-bash"], "timeout": 30, "statusMessage": "qbit-vault hook post-bash" }] },
      { "matcher": "Read", "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "post-read"], "timeout": 30, "statusMessage": "qbit-vault hook post-read" }] },
      { "matcher": "Grep|Glob", "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "post-read"], "timeout": 30, "statusMessage": "qbit-vault search output guard" }] }
    ],
    "UserPromptSubmit": [{ "hooks": [{ "type": "command", "command": "/usr/local/bin/qbit-vault", "args": ["hook", "user-prompt"], "timeout": 30, "statusMessage": "qbit-vault hook user-prompt" }] }]
  },
  "permissions": { "deny": ["Read(//home/me/.qbit-vault/**)", "Edit(//home/me/.qbit-vault/**)"] }
}
```

Decisions behind the shapes:
- **Exec form.** `command` is the binary and `args` its arguments (<https://code.claude.com/docs/en/hooks.md> § Exec form and shell form): no shell parses the line, so a path with spaces (`C:\Program Files\QBit Vault\qbit-vault.exe`) needs no quoting. On Windows exec form needs a real `.exe`, which `qbit-vault.exe` is. The hooks always exit 0 (S6, fail open), so `onFailure` is left unset.
- **Ownership marker.** Exec form leaves no `qbit-vault hook` text in `command`, so each entry carries it in `statusMessage` (the spinner text Claude Code shows while the hook runs): `qbit-vault hook pre-bash`, `... post-bash`, `... post-read`, `... pre-write`, `... user-prompt`, and `qbit-vault search output guard` for the Grep and Glob entry, which runs the same `post-read` command as the Read one and so cannot share its marker (markers match by substring). A registration written by an older version gets the two new entries (Grep and Glob output, file writes) added on the next `sync` or `init`, with a snapshot of `settings.json` first. Re-running `init` replaces exactly those entries (also after the binary moved) and never touches another tool's hook, Gentle AI's included.
- **Deny rules use the resolved vault home in Claude Code's absolute form** `//path` (a single leading slash would anchor at `~/.claude`; on Windows `C:\Users\me\.qbit-vault` is written `//c/Users/me/.qbit-vault`; <https://code.claude.com/docs/en/permissions.md> § How path patterns match). `Read` also stops the `cat`/`head`/`tail` that Claude Code recognizes in Bash; `Edit` covers the write tools (a `Write(...)` rule never matches). A shell that reads the directory by another route is not stopped, which is why no secret is ever in the agent's environment either. Each entry is owned by its full string; the user's other entries keep their place and order.
- **Timeouts.** 10 s for `pre-bash` (never opens the vault), 30 s for the others (`pre-write` reads the vault like the post hooks).
- **Not honored yet:** `CLAUDE_CONFIG_DIR` (a relocated Claude Code config) is not read; the adapter writes under the user home.

Hook semantics (Claude Code hook protocol):
- `pre-bash` (implemented; the rewrite below is not, see "What `pre-bash` does today"): reads `{session_id, tool_input.command, cwd}`; if the command references known secrets or an implicit binding matches, returns `hookSpecificOutput.updatedInput.command = "qbit-vault exec --session claude:<session_id> --secret … -- <cmd>"`. If a referenced secret has no grant, returns `permissionDecision: "deny"` with reason `grant_required: NAME — call secret_request`. Dump-guard violations: deny with `dump_command`.
- `post-bash` / `post-read` (implemented, see "What the post and prompt hooks do today"): read `tool_response`; return it redacted via `hookSpecificOutput.updatedToolOutput` (it must keep the tool's output shape, see below). This path is a last line of defense, the pre hook is the real control.
- `pre-write` (implemented, see "Output and write guard"): reads the tool input of a file write or edit and denies it when the text it would add to a file carries the value of a stored `secret` entry (text it removes does not count).
- `user-prompt` (implemented): blocks a prompt that carries the value of a stored `secret` entry or a well-known secret shape, with a reason telling the user to store it with `qbit-vault set NAME`. The `/vault set NAME` shortcut and `config.paste_capture: true` (open the native prompt immediately) are not implemented.

#### Hook protocol (verified)

Checked on 2026-11-04 against the official reference, <https://code.claude.com/docs/en/hooks.md> (the page `docs.claude.com/en/docs/claude-code/hooks` now serves). Re-verify when Claude Code changes major behavior; `internal/hook/testdata` holds recorded events.

- **Input.** One JSON object on stdin. Common fields: `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, plus `tool_name`, `tool_input`, `tool_use_id` for tool events. Bash: `tool_input.command` (also `description`, `timeout`, `run_in_background`). **PowerShell is a separate tool** with the same `tool_input.command`; on Windows without Git Bash there is no Bash tool at all, so matchers must be `Bash|PowerShell`. Read: `tool_input.file_path`.
- **Exit codes.** 0 = success, stdout JSON applies. **2 = blocking error** (PreToolUse blocks the call, stderr is the reason; JSON cannot override it). **Any other code, a crash, or unparseable/invalid JSON = non-blocking error**: the action proceeds and the user sees a `hook error` notice. Claude never sees stderr of a hook that exits 0. So qbit-vault hooks always exit 0 and speak only through stdout JSON.
- **stdout.** Exactly one JSON object and nothing else. Empty stdout with exit 0 means no opinion: the normal permission flow applies.
- **PreToolUse decision** is `hookSpecificOutput`: `hookEventName: "PreToolUse"`, `permissionDecision` `allow|deny|ask|defer`, `permissionDecisionReason` (shown to Claude for `deny`, to the user for `ask`, debug log only for `allow`), `updatedInput` (replaces the **whole** `tool_input`, so repeat unchanged fields), `additionalContext` (added next to the tool result). **`allow` skips the permission prompt**, so a hook that only wants to warn or stay out of the way must not send it. Precedence across hooks: `deny` > `defer` > `ask` > `allow`. The top-level `decision`/`reason` for this event are deprecated.
- **Warnings.** `systemMessage` (any event) is shown to the user; `additionalContext` reaches Claude as a system reminder next to the tool result (PreToolUse, PostToolUse, UserPromptSubmit and others). Each is capped at 10,000 characters. qbit-vault's fail-open answer uses both.
- **PostToolUse** (tool already ran, cannot be undone): input adds `tool_response` (Bash: `stdout`, `stderr`, `interrupted`, `isImage`) and `duration_ms`. Output: `hookSpecificOutput.updatedToolOutput` **replaces** the tool result Claude sees (it must match the tool's output shape; for built-in tools a mismatch is ignored and the original is kept; it does not change telemetry or what the user's terminal showed); `additionalContext`; top-level `decision: "block"` + `reason` only adds the reason next to the result, Claude still sees the original. Exit 2 shows stderr to Claude. Redaction is therefore possible; the shapes P3b uses are under "What the post and prompt hooks do today".
- **UserPromptSubmit**: input adds `prompt` (pasted text arrives expanded; it may be wrapped in `<pasted_content id=…>` lines). Output: top-level `decision: "block"` + `reason` (shown to the user, not to Claude), `hookSpecificOutput.additionalContext` (to Claude), `sessionTitle`, `suppressOriginalPrompt`. It **cannot rewrite the prompt**. Plain-text stdout on exit 0 is also added to Claude's context. A blocked prompt's text still lands in the transcript and prompt history unless `suppressOriginalPrompt: true` is set, and even then it can remain in local files.

Differences from what this document said before: the PostToolUse replacement field is `updatedToolOutput` (not `updatedResponse`); the post commands are `hook post-bash` and `hook post-read` (CLI.md), not `hook post`; the PreToolUse matcher includes `PowerShell`.

#### What `pre-bash` does today

`qbit-vault hook pre-bash` (internal/hook) never opens the vault, prompts or uses the network (the post and prompt hooks below do read the vault); a run takes microseconds in-process and tens of milliseconds as a process on Windows.

- It splits the command across `&&`, `||`, `;`, `|`, `&`, newlines, `( )`, `$( )` and backticks (also inside double quotes), strips env assignments, redirections, `sudo`/`doas`/`env`/`exec`/`command`/`builtin`/`nohup`/`time`/`nice`/`xargs`/`timeout`, and looks inside `sh|bash|zsh|dash|ksh|fish|pwsh|powershell|cmd -c|-Command|/c` strings, `npx|bunx|pnpx|npm exec|pnpm dlx|yarn dlx|bun x` (with `@version`), and the command after `--` of `qbit-vault exec`. A program is `qbit-vault` by its base name, case-insensitive, with or without `.exe`/`.cmd`/`.bat`/`.ps1`, at any path. `pwsh`/`powershell` with an encoded command (`-e`, `-ec`, `-enc`, `-EncodedCommand`, any case, `-` or `/`) is refused too: its base64 script cannot be read.
- **Agent may run** (no output, the host's permission flow applies): no subcommand (bare, `--help`, `--version`), and `version`, `help`, `list`, `describe`, `grants`, `audit` (including `--verify`), `doctor`, and `exec` (its grants are the control; the command after `--` is checked recursively).
- **Denied** with `permissionDecision: "deny"` and the fixed reason `This qbit-vault command is user-only: ask the user to run it in their own terminal. The agent's shell cannot run it.` (the command is never echoed): every other subcommand, so `set rm mv edit relink link import restore rekey lock unlock grant revoke init uninstall sync update prompt mcp broker hook` and `remote` with any or no sub-subcommand (R-SYNC-05), and any unknown name. A line that mentions `qbit-vault` but cannot be parsed (unbalanced quote or substitution, here-document) or goes through `eval`/`iex`/`Invoke-Expression`/`Start-Process`/`Invoke-Command` is denied too.
- **Fails open** (S6): unreadable or oversized stdin, malformed JSON, a wrong `command` type, a handler error or a panic gives exit 0 and `{"systemMessage":…,"hookSpecificOutput":{"hookEventName":"PreToolUse","additionalContext":…}}` with the text `qbit-vault hook failed; the command ran without its checks; run 'qbit-vault doctor'`, and no `permissionDecision`. A detected forbidden invocation is never a failure: it is always denied.
- **Not done yet (pre-bash):** rewriting commands that reference bound secrets into `qbit-vault exec` (R-EXEC-02) and the `grant_required` / `dump_command` denials need the vault's names, bindings and grants; they belong to the slice that loads bindings (P3b or later). Until then such commands pass through unchanged, and the secret is simply absent from the agent's environment.
- **Limits.** The scanner is a guard against the model running a user-only command by mistake or by prompt injection, not a sandbox: an invocation built at run time (base64, `$VAR` as program, a script file) is not seen. The real controls are that those commands need the user's own prompt backend (`not_model_callable`, R-SYNC-05) and that no secret is in the agent's environment.

#### What the post and prompt hooks do today

`hook post-bash`, `hook post-read` and `hook user-prompt` (internal/hook, `internal/cli/hookcmd.go`) redact or block using the values in the vault. They open it **without prompting**, the way `remote status` does: through the OS keychain or an unexpired unlock cache, never a passphrase prompt, and they never finish an interrupted rekey.

- **Which values.** Every stored value of at least 8 bytes (`redact.ShortLen`), in every layer, plus shorter values that have an active grant (any session). A value the agent reads from a file or a log is a leak whether or not a grant covers it, so grants do not gate redaction; shorter values without a grant are skipped because redacting three or four characters would mangle ordinary output. `exec` redacts its injected values whatever their length. Encodings are the ones `internal/redact` knows: raw, base64 (standard and URL-safe, padded or not, also inside a larger base64 blob), percent-encoding, JSON-escaped, UTF-16LE and UTF-16BE (a file written by Windows PowerShell 5.1 `Out-File`), and the value with surrounding quotes. The marker is `[REDACTED:NAME]`.
- **Shape.** The hook decodes `tool_response`, redacts every string value inside it (never keys), and re-emits the same structure as `hookSpecificOutput.updatedToolOutput`, so the replacement has the shape of the original by construction. Bash and PowerShell: `{stdout, stderr, interrupted, isImage}` (documented). Read: `{type, file: {filePath, content, numLines, startLine, totalLines}}`; the official reference does not document Read's output object, this is the shape Claude Code produced when recorded (`testdata/posttooluse_read.json`), and the hook does not depend on it. Object keys come back in alphabetical order, which JSON does not care about. The answer also carries `additionalContext`: `qbit-vault redacted N occurrence(s) of stored secrets`. When nothing matched, nothing is printed.
- **Size.** A PostToolUse event is read up to 64 MiB and the whole output is redacted (memory is a few times the event size). A bigger event is not parsed: when the vault has values to check, the output is withheld (`output too large`), because the shape of the result is unknown it is replaced by a bare string; hosts cap tool output far below this.
- **Cost.** No vault open when the result holds no text. With a vault: opening it, listing the records and redacting a 2 KB output took about 65 ms in-process on Windows with ten secrets (23 ms of that is the test harness); as a process the run is dominated by process start (about 85 ms here, the same as `qbit-vault version`).
- **Locked vault.** A passphrase vault with no unlock cache (or a vault the keychain cannot give a key for) cannot be read without a prompt. `post-bash` and `post-read` then **withhold the output** instead of letting it through (see "Output and write guard"); `user-prompt` still fails open with `qbit-vault could not check this prompt for secrets (vault locked); a QBit Vault tool call such as secret_list opens the unlock dialog` in `systemMessage` and `additionalContext`: the hooks never open the dialog, but the agent's next QBit Vault tool call does (above), and from then on the hooks redact again. An event that is not JSON gives the generic warning of pre-bash. A home with no vault is silent: there is nothing to redact.
- **`user-prompt`.** A prompt that contains the value of a stored `kind: secret` entry (any encoding above, including inside `<pasted_content>` blocks) is blocked. The value of a `kind: text` entry (a URL, a host, a region: stored so commands can use it, typed in the chat all the time) does not block a prompt and is never named in a reason; `post-bash` and `post-read` still redact it, and a well-known secret shape still blocks whatever the entry kind. A blocked prompt gets: `{"decision":"block","reason":"This message contains the value of the stored secret GITHUB_TOKEN, so qbit-vault blocked it. <advice>","hookSpecificOutput":{"hookEventName":"UserPromptSubmit","suppressOriginalPrompt":true}}`. The reason names every stored entry whose value matched, by name only, sorted and without repeats, at most 5 then `and N more` (`... of the stored secrets A, B, ...`); names are read from the redacted text, and a `[REDACTED:X]` already in the message is not reported. It never includes the message, a value or any part of one, and `suppressOriginalPrompt` keeps the text out of the block message. `<advice>` is fixed: `If you typed or pasted it, store it with 'qbit-vault set NAME' in your own terminal and refer to it by name. If it came from a background job or another agent's report, the command printed the value: run it through qbit-vault (secret_exec), which redacts its output.` **Why it blocks instead of redacting:** the host cannot rewrite a prompt from this hook (it can only block it or add context next to it, and nothing tells a typed message from a harness notification such as a finished background job), and letting the message through would hand the value to the model. The advice and the agent skill therefore move the cause out of the way: a job that uses a credential runs through `secret_exec`, whose output and completion notice are already redacted. A prompt that matches a well-known secret shape (`ghp_`/`gho_`/`ghs_`, `github_pat_`, `AKIA`/`ASIA` keys, `xox*-` Slack tokens, `sk_live_`/`rk_live_`, `sk-`/`sk-ant-`/`sk-proj-` keys of 32 or more characters, PEM private key headers, JWTs) is blocked too, naming the kind and never the text: `This message looks like it contains a GitHub token, so qbit-vault blocked it. <advice>` (kinds: GitHub token, GitHub fine-grained token, AWS access key, Slack token, Stripe live key, API key, private key, JWT; with several shapes in one message the first in this order is named); that check needs no vault, so it works while the vault is locked. Generic high-entropy strings are not matched (too many false positives). **Limit:** a blocked prompt still lands in the transcript and the prompt history (Claude Code writes them before the hook can act); the hook cannot remove it, only keep it out of the block message.
- **Limits.** Redaction happens after the tool ran and only changes what the model sees; telemetry and the user's terminal keep the original. A value the shell transformed (hex, ROT13, split across lines of a table) is not recognized.

#### Output and write guard

One rule in the binary, wired into each host's own mechanism (odd/tasks/output-guard.md): the agent's built-in tool output is redacted for every stored value, a file write or edit that carries a stored value is denied, and when the check cannot run while it may matter the output is withheld instead of passed through.

| Host | Output redaction | Write guard | Status |
| --- | --- | --- | --- |
| Claude Code | `PostToolUse` on `Bash\|PowerShell` (`hook post-bash`), `Read` and `Grep\|Glob` (`hook post-read`) | `PreToolUse` on `Write\|Edit\|MultiEdit\|NotebookEdit` (`hook pre-write`) | built, registered by `init` and `sync` |
| Codex | `PostToolUse` on `Bash` (`hook post-bash --host codex`) | `PreToolUse` on `apply_patch` (`hook pre-write --host codex`) | built, registered by `init` and `sync` in `~/.codex/hooks.json`; Codex runs them only after the user trusts them in `/hooks` |
| Pi | `tool_result` handler of the extension `qbit-vault-pi` ≥ 0.2.1 for `bash`/`powershell` (`hook post-bash --host pi`) and `read`/`grep`/`find`/`ls` (`hook post-read --host pi`) | `tool_call` handler for `write` (`content`) and `edit` (`edits[].newText`) (`hook pre-write --host pi`) | built in the extension (installed by the user, not by `init`); with no extension Pi has no guard |

- **Fail mode.** No vault, or nothing to redact: everything passes unchanged and nothing is printed (no prompt, no warning). Values to check but the check fails: a locked vault (it cannot tell whether values are active), a vault error, a panic, or an event over 64 MiB. Then the whole output is replaced by exactly `output withheld: qbit-vault could not check it for secrets (<reason>)`, and a write is denied with exactly `qbit-vault could not check this edit for secrets (<reason>)`. The reason is a fixed string, never an error text: `vault locked`, `output too large` (`edit too large` for a write) or `internal error`. An event that is not JSON has no output to replace and fails open with the generic warning.
- **Withheld shape.** The replacement keeps the structure of the tool result: every string is emptied and the text goes into the member that carries the output (`stdout`, then `content`, `output`, `text`, `result`, else the longest string), so nothing of the original survives; the host would ignore a replacement of another shape and keep the original.
- **Write guard.** The text the call would add to a file is scanned for every stored `secret` value in all the encodings of `internal/redact` (a `text` entry does not count, as in `user-prompt`). Only added text is scanned, so removing a stored value from a file is allowed: Claude `Write.content`, `Edit.new_string`, `MultiEdit.edits[].new_string`, `NotebookEdit.new_source`; Pi `write.content`, `edit.edits[].newText`; Codex `apply_patch` (V4A text in `tool_input.command`): the `+` lines of `*** Add File` and of the `*** Update File` hunks, never ` ` context or `-` lines. The name of the file written is scanned too (`file_path`, `path`, `notebook_path`, and the `*** Add File`, `*** Update File` and `*** Move to` headers), since a file name reaches the disk as well. A tool or input shape not in that list (another tool, an unexpected member, a `command` that is not a patch) is scanned whole. A hit denies the call with `This edit would write the value of the stored secret NAME to a file, so qbit-vault blocked it. Give the value to the command that needs it with secret_exec instead.` (several names: `secrets A, B`, sorted, at most 5 then `and N more`; names only, never the value or the content).
- **`--host`.** `hook post-bash`, `hook post-read` and `hook pre-write` take `--host claude|codex|pi` (default `claude`, so registrations written before it keep working). `claude` and `pi` answer `hookSpecificOutput.updatedToolOutput` (post) and `permissionDecision: deny` (pre-write). `codex` answers a changed or withheld PostToolUse with `{"decision":"block","reason":"<redacted or withheld output>"}`, which Codex shows in place of the tool result (the redacted text when the result is a string, its compact JSON otherwise), and a PreToolUse denial with `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":"<message>"}}`. No change: no output on any host.
- **Codex limit.** Codex shows the model about 2,500 tokens of one hook message and spills the rest to a file (https://learn.chatgpt.com/docs/hooks.md § Large hook output). A redacted block reason above 8,000 bytes (`hook.CodexReasonLimit`, a conservative reading of 2,500 tokens at about 4 bytes each) is cut after the redaction, on a character boundary and never inside a `[REDACTED:NAME]` marker, and ends with the line `[output truncated by qbit-vault]`; the withheld text is short and never cut. Only `Bash` and `apply_patch` are registered: Codex has no read, grep or glob tool of its own (it reads through the shell), and MCP tool output is not covered, because `updatedMCPToolOutput` is parsed by Codex but not supported. Codex itself calls its hooks "a useful guardrail, not a complete enforcement boundary".
- **Pi.** The extension has no hook protocol of its own to fail open on: it spawns the hook and applies the fail mode itself. No binary: pass. A timeout (30 s), a crash, a start failure or an answer it cannot read: the output is replaced by `output withheld: qbit-vault could not check it for secrets (timeout)` or `(internal error)`, and the edit is blocked with `qbit-vault could not check this edit for secrets (<reason>)`. The tool result is sent as `tool_response` `{stdout, structuredContent}` on stdin, and the answer's `stdout` replaces the text blocks (images stay); `structuredContent` is dropped, never kept (Pi drops it when `content` is replaced).
- **Residual.** A host's own hook timeout or crash fails open on Claude Code and Codex; streaming partial output in Pi is not covered; a value split across two tool results is not caught.

**Codex** (adapter `codex`, `internal/hosts/codex`; three steps: `mcp` in `~/.codex/config.toml`, merged; `hooks` in `~/.codex/hooks.json`, merged, below; and `skill`, `~/.agents/skills/qbit-vault/SKILL.md`, § Agent skill):

```toml
# only when the vault home is not ~/.qbit-vault:
```

Format checked against https://developers.openai.com/codex/mcp (§ Configure with config.toml) on 2026-11-04: `[mcp_servers.<name>]` tables with `command` (required), `args`, `env`, `startup_timeout_sec` (default 10) and `tool_timeout_sec` (default 60). `init` writes only `command`, `args` and, for a custom vault home, the `env` subtable; the timeouts keep Codex's defaults. `command` is the absolute path of the running binary, written as a TOML basic string (backslashes and quotes escaped).

Only our table is edited, as text, through `internal/filemerge`: every other byte of `config.toml` (comments, other `[mcp_servers.*]` tables, line endings, a missing final newline) stays identical, the file is snapshotted first and written atomically, and `uninstall` removes just our table. A config that defines our table in a form the editor cannot edit safely (inline table, dotted keys, an array of tables, a table defined twice) is refused and left untouched. Detection: `~/.codex` is a directory or `codex` is on `PATH`.

Sandbox note: `init` does **not** set `QBIT_VAULT_PROMPT`. The Codex docs (checked 2026-11-04) say nothing that requires it, and the sandbox they describe governs the shell commands the model runs; Codex spawns MCP servers itself, as ordinary child processes, so we expect the native dialog to open as it does from any other process (not yet verified end to end inside a Codex session). Forcing `tty` would be wrong by default: an MCP server's stdin and stdout are the protocol pipe, and the terminal prompt needs a controlling terminal, which the server may not have. The prompt already falls back to the terminal on its own when there is no desktop session (§ Native capture dialog). A user whose setup does block the dialog can add `QBIT_VAULT_PROMPT = "tty"` to the `env` subtable by hand; since that table is ours, `doctor` then reports drift and the next `init` rewrites it; there is no supported override in this release.

`hooks` step: `~/.codex/hooks.json`, through `internal/filemerge` like the Claude settings. {"hooks": {
```json
  "PostToolUse": [{"matcher": "Bash", "hooks": [{"type": "command", "command": "/abs/path/to/qbit-vault hook post-bash --host codex", "commandWindows": "& 'C:\\abs\\path\\qbit-vault.exe' hook post-bash --host codex", "timeout": 30, "statusMessage": "qbit-vault hook post-bash"}]}],
  "PreToolUse":  [{"matcher": "apply_patch", "hooks": [{"type": "command", "command": "/abs/path/to/qbit-vault hook pre-write --host codex", "commandWindows": "& 'C:\\abs\\path\\qbit-vault.exe' hook pre-write --host codex", "timeout": 30, "statusMessage": "qbit-vault hook pre-write"}]}]

```

Verified against https://learn.chatgpt.com/docs/hooks.md on 2026-11-11 (Codex 0.166.0 installed): a handler has `type`, `command` (a shell command line, not an argv) with the Windows-only override `commandWindows`, `timeout` in seconds (Codex's default is 600) and `statusMessage`; the matcher is a regex on the tool name, and `apply_patch` also matches the aliases `Edit` and `Write`. `PostToolUse` input carries `tool_name`, `tool_input` and `tool_response` and fires for non-zero exits too; `decision: "block"` replaces the tool result with the `reason`. For `apply_patch` the patch text is `tool_input.command`, and a denial is `hookSpecificOutput.permissionDecision: "deny"`.

**Quoting the executable (S10.1).** The executable path is one word of a shell command line, so it is quoted for the shell that reads it. `command` is quoted for sh: bare when it has only `A-Za-z0-9/._-+:@=,`, otherwise in single quotes, where only the quote itself is escaped (`'` becomes close, escaped quote, reopen), which carries spaces, `"`, `$`, backticks, `%`, `!`, `&`, parentheses, non-ASCII and backslashes. `commandWindows` (Codex' documented Windows-only override) is a PowerShell call, `& '<path>'`, where the quote is doubled and so are the typographic single quotes U+2018 to U+201B, which PowerShell also reads as quotes. The only path refused is one hooks.json cannot hold (not valid UTF-8, or a NUL); then `init` and `sync` print `host codex: failed at hooks` followed by `Codex output guard not installed: the qbit-vault path cannot be written into a hook command (it is not valid UTF-8). Reinstall qbit-vault in another folder and run 'qbit-vault sync'.`, and `doctor` warns on `host.codex.executable` with the same cause. The other steps of the host (MCP server, skill) still register.

Which shell runs the command, verified and assumed (2026-11-11, Codex 0.166.0): the docs say `command` is "a shell command line", show `$(git rev-parse --show-toplevel)` in an example (so a POSIX shell expands it on Linux and macOS), and offer `commandWindows` as the Windows override. The installed binary (read-only strings; Codex was not run) wraps hooks that run in a remote environment as a PowerShell pipeline on Windows (`[Console]::In.ReadLine() | <command>`, with the error `environment command hooks require PowerShell on Windows`) and as `read -r …; printf … | ( <command> )` for sh elsewhere. Not stated anywhere: that a hook of the local machine uses the same shell. So the PowerShell form for Windows and the sh form elsewhere are the best-supported reading, not a verified fact; if Codex ran `commandWindows` with cmd.exe, the guard would fail to start and Codex fails open, which `doctor` cannot see.

**Trust.** Codex runs a non-managed hook only after the user reviews and trusts its exact definition (`/hooks` in the CLI, **Review hooks** in the app). The trust is recorded against a hash of the definition (`[hooks.state…]` in `config.toml`), and a new or changed hook is skipped until trusted. qbit-vault never writes that state (trusting code to run is the user's decision): `init` and `sync` print `Codex skips new hooks until you trust them: open /hooks in Codex and trust the qbit-vault hooks.` when they wrote the hooks. Until then the guard does not run, and `doctor` cannot tell, because it reports the file and not Codex's trust state. The hash covers the command line, so a moved binary needs a new review. Hook errors fail open on Codex's side.

Not verified (no Codex session was run, and the real `~/.codex` was not read): the exact JSON shape of `tool_response` for `Bash` (the docs say "model-facing output"; the hook redacts every string of whatever JSON arrives and sends a string result as it is), which shell Codex uses for a hook of the local machine (see above), and whether the 2,500-token cap counts like the 8,000-byte limit assumes.

## Agent skill

The MCP instructions and the four tool descriptions say *what* the tools do; the `qbit-vault` skill says *when* to reach for them: whenever a command needs a credential, call `secret_list`, then `secret_request` for what is missing, then `secret_exec`; never ask the user to paste a value; what to do with each refusal. Source: `internal/hosts/skill/SKILL.md`, embedded in the binary.

| Host | Skill file | Why there |
| --- | --- | --- |
| Claude Code | `~/.claude/skills/qbit-vault/SKILL.md` | Claude Code's personal skills directory |
| Codex | `~/.agents/skills/qbit-vault/SKILL.md` | Codex reads user skills from `~/.agents/skills` (`~/.codex/skills` is its legacy name; openai/codex#10437, checked 2026-11-05) |
| Pi | the same file as Codex | Pi reads `~/.agents/skills` too; a second copy in `~/.pi/agent/skills` would collide by name |

Rules (step `skill`, `internal/hosts/skill`, written with `filemerge.WriteOwnedFile`):

- **Only where it is needed.** Only registered hosts get it, and the file is written only when its bytes differ from the skill this build carries: a current copy is never rewritten, snapshotted or re-recorded. The skill text has no version string, so a release that does not change it touches nothing.
- **Always current.** `sync` rewrites a stale copy (snapshot first), and `install.sh` / `install.ps1` run `sync` after every upgrade, so each release installs its own skill. `doctor` reports a stale or missing copy as `host.<name>.skill` drift (`run 'qbit-vault sync'`).
- **Whole file, ours only.** The file carries the marker `<!-- Managed by qbit-vault:`. A `SKILL.md` at that path without it is the user's own skill of that name and wins: the step records it without writing, `doctor` accepts it, and `uninstall` leaves it; registration does not fail because of it. Edits to our file are replaced by the next `sync`; keep your own notes in another skill.
- **Uninstall.** `uninstall` deletes our copy (snapshot first) and its directory when empty; a copy the user replaced (no marker) stays. The shared Codex/Pi file stays while the other host is still registered. qbit-vault never writes `CLAUDE.md`, `AGENTS.md` or any other instruction file of the user.

## Native capture dialog (non-Pi hosts)

`qbit-vault prompt`, `set`, `grant` and every other command that asks the user pick a backend in the same order. With `QBIT_VAULT_PROMPT` unset: the platform's **native dialog when a desktop session is available**, otherwise the terminal. `QBIT_VAULT_PROMPT=tty|powershell|osascript|zenity|kdialog` forces one; a named backend that is not installed fails with `prompt backend <name> is unavailable` and never falls back to another one.

| OS | Backend | Mechanism | Used when |
| --- | --- | --- | --- |
| Windows | `powershell` | `powershell.exe -NoProfile -NonInteractive -STA -Command -` with a WinForms script on stdin: a TopMost dialog, masked `TextBox` (`UseSystemPasswordChar`), radio buttons for layer and scope, `Confirm` / `Decline` or `OK` / `Cancel` buttons | the process runs in an interactive session (not session 0) and `powershell.exe` exists at `%SystemRoot%\System32\WindowsPowerShell\v1.0\` |
| macOS | `osascript` | `display dialog ... with hidden answer` for the value, `choose from list` for layer and scope, `display dialog` with `Decline` / `Confirm` buttons; the script is sent on stdin | `/usr/bin/osascript` exists, and the shell is not an SSH session without a GUI (`SSH_CONNECTION` or `SSH_TTY` set and neither `__CFBundleIdentifier` nor `TERM_PROGRAM` set) |
| WSL | `powershell` | the same Windows dialogs as the Windows row, started from Linux: `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe` with the same arguments and the script on stdin; the value comes back on its stdout pipe as UTF-8 bytes, never through a file, an argument or the environment | the process runs under WSL (`WSL_DISTRO_NAME` set or `/proc/sys/fs/binfmt_misc/WSLInterop` present) and that file exists. It is tried before `zenity` and `kdialog` and does not depend on `DISPLAY` (WSLg sets it, but the Windows desktop is where the user is) |
| Linux (desktop) | `zenity` or `kdialog` | zenity: `--entry --hide-text` for the value (`--password` has no text field, so it could not show the request), `--list --radiolist`, `--question`; kdialog: `--password`, `--radiolist` (a confirmation too: Decline preselected, because `--yesno` cannot default to no and Escape answers like its no button). zenity is tried first; kdialog renders every text as rich text, so the request is HTML-escaped and its layout lines become `<br>` | `DISPLAY` or `WAYLAND_DISPLAY` is set and one of the two is on `PATH` |
| Any | `tty` | opens `/dev/tty` (`CONIN$` on Windows), disables echo, reads value, prints the scope choice menu | the fallback, or `QBIT_VAULT_PROMPT=tty` |

The dialog always shows: secret name, the reason verbatim (control and bidi characters shown as visible escapes, so a reason cannot add a line or paint over the dialog), the host and session id, the project label (or `global`), and whether the value is **new** or **already stored (it will be replaced)**. When the value is new and `cwd` is inside a repository, the dialog also asks for the layer (`Global` / `This project`). For `secret_manage` the same backends render a confirmation (opened by the broker itself; a `prompt --confirm` command for hosts is planned, slice 4.3) with the action, the diff and `Confirm` / `Decline`; closing the dialog or pressing Esc is `Decline`, and on Windows and macOS so is Enter (the default button). A passphrase asked twice (`init`) is two dialogs.

**Several fields in one prompt** (CONTRACT `request` with `fields`, R-CAP-08). The request text, the layer question and the scope choice appear once; every new field gets its own box labelled with its `label` (default the name), masked for `secret` and visible for `text`; stored fields are listed as *already stored* without a box. PowerShell renders one WinForms form with one `TextBox` per field (`UseSystemPasswordChar` only on secret ones; each value comes back as one base64 line on the helper's private stdout); zenity uses one `--forms` dialog (`--add-password` for secret fields, `--add-entry` for text ones, answers split on a control-character separator); osascript and kdialog have no multi-field form, so they show one box per field in a row, each repeating the request header and a `field 2 of 3` line, and cancelling any box cancels the whole capture; the terminal does the same with one line per field (echo off for secret fields, on for text fields). Empty boxes, a cancel or the timeout store nothing (R-CAP-04).

**Remote sync prompts.** `remote register`, `join`, `approve`, `revoke-device`, `recovery-key --rotate`, `resolve`, `restore`, `logout` and `link` ask and display through the same backends: the invite code and the recovery key in a masked box, the pairing code and the confirmation code as plain masked questions (the confirmation code under its own `Confirmation code` heading, with no request lines), and the recovery key and the confirmation code shown in a dialog (or on the controlling terminal) that is never the command's stdout (`REMOTE_SYNC.md` § 4).

**One voice.** The same words appear on Windows, macOS, Linux and the terminal. Every native window is titled `QBit Vault`; the heading inside says what it is: `Secret request`, `Permission request` (a question about letting an agent use a secret), `Confirm`, `Recovery key`, `Confirmation code` (the code `remote approve` shows), `Vault passphrase` or `Export passphrase`. Buttons say the action where the helper can set them: `Save` / `Cancel` for a secret or a form, `Continue` / `Cancel` for a menu or a passphrase, `Done` / `Cancel` for the recovery key and the confirmation code, and `Confirm` / `Decline` for a yes/no question, where Enter is `Decline` (on Windows `Decline` is the highlighted button). The permission question names who asks, then the reason on its own line: `Claude Code wants to use GITHUB_TOKEN (all projects).` and `Why: <reason>`. Layers read `all projects` or `project <label>` in the text and `All projects` / `Only this project (<label>)` in the pickers. A new passphrase that does not match its confirmation is asked again, up to 3 times in total (the dialog starts with `Passphrases do not match. Try again.`; the terminal prints `Passphrases do not match.`). A passphrase says what it protects: `Vault passphrase`, `Export passphrase (protects this backup file)` (then `Type the export passphrase again`) or `Passphrase of the export file`. The request lines (Who, Secret, Why, Saved in, Value) are a two-column grid on Windows and aligned text elsewhere; the several-fields form has no Value line, each box says `(hidden)` or `(shown while you type)`. zenity dialogs are 480 px wide and their lists have no `Pick` or `Index` headers; osascript uses the `note` icon, and `caution` only for a removal. On the terminal Ctrl-C at a menu, a y/N question or a Press-Enter screen is `cancelled`, as in a hidden read, and does not kill the process.

**Showing what the user must keep.** The recovery key and the pairing confirmation code (REMOTE_SYNC.md § 4) are shown out of band, never on stdout, stderr or `--json`. Their text never travels in a helper's argv, because any local user can read a process's command line: PowerShell and osascript get it inside the script on stdin, zenity through `--text-info` reading stdin, the terminal backend writes it to the controlling terminal and waits for Enter. kdialog takes text only as arguments, so on a Linux that has only kdialog these two screens are shown on the controlling terminal instead (the text, then `Press Enter when done.`); with no terminal either the command reports `prompt backend unavailable`. Every line is escaped like any request text.

**Where the helper is found.** `powershell.exe` and `osascript` are run from their fixed system locations and are never looked up on `PATH`, because anything that can put a file earlier on `PATH` could stand in for the dialog and receive the value. On Windows the directory comes from the system API (`GetSystemWindowsDirectory`), with `C:\Windows` as fallback, and the file must exist; from WSL, `powershell` is `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe` (chosen by default under WSL, or by forcing it) when it exists. `qbit-vault doctor` shows the choice (`prompt: powershell (WSL)`). `zenity` and `kdialog` have no single fixed location on Linux, but they are not taken from `PATH` either: they are looked up only in `/usr/bin`, `/bin` and `/usr/local/bin`, in that order, and the backend is unavailable when none holds them. No helper is located through `PATH`.

**Input rules, identical on every backend.** A secret value loses its line terminator and surrounding whitespace (R-CAP-04, the same `bytes.TrimSpace` rule as `set --stdin`). A passphrase loses only its line terminator, never other whitespace, so the same passphrase derives the same key whether it was typed in a dialog, on the terminal or given to `init --passphrase-stdin`. Input longer than the read bound (64 KiB plus margin) is refused with `value too large` and wiped, never truncated.

**How the value comes back.** The value never travels on qbit-vault's own stdout, which the host can read. It comes back on the **helper's** stdout: a private anonymous pipe between the dialog helper and qbit-vault that the agent does not hold. The helper's script or arguments carry the request text only (for PowerShell as base64 data, for AppleScript as escaped literals, for zenity and kdialog as single argv elements), never a value, and the helper's environment is qbit-vault's own with nothing added. qbit-vault reads the pipe as bytes into one buffer and wipes it after copying the value into a `Secret`; a failing or cancelled helper yields only a typed error (`cancelled`, `No answer in time; nothing was saved.`, or `prompt backend unavailable`) with none of the helper's output. A dialog that cannot open when it was selected (no display, helper crashed) is the unavailable error, not a silent retry on the terminal.

`prompt --value` hands the value to the host on file descriptor 3, which POSIX hosts can open. Windows does not pass numbered descriptors to child processes, so there `--value` is refused; a Windows host captures with its own prompt (the Pi extension's masked input) or lets `set` open the native dialog, and stores with `set --stdin`.

## Subagents

A subagent is a new session id. Over MCP, each MCP server process uses `QBIT_VAULT_SESSION` or generates its own `mcp:<16 hex>`, so a subagent with its own server needs its own grants. Planned with the extension and the hook rewrite: Pi subagents and Gentle Agents get `pi:<child-id>`, and Claude Code subagents (same `session_id`, distinct `agent_id`) get `claude:<session_id>/<agent_id>`. No grant inheritance (R-GRANT-05). The user sees a separate prompt naming the session.
