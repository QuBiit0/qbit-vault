# CLI reference

`qbit-vault [global flags] <command> [flags]`

Everything below is built unless a row says *planned*. Command names, flags and defaults were checked against `qbit-vault <command> --help`.

Global flags: `--home <dir>` (default `$QBIT_VAULT_HOME` or `~/.qbit-vault`), `--json` (machine output, exactly one JSON object on stdout), `--session <id>` (host session; required by `exec`, `set --grant`, `grant`, `revoke --session-only`), `--quiet`, `--no-color`.

Values are **never** accepted as arguments. `set` and `import` read from the hidden prompt or stdin.

**Layers.** Every secret is either `global` or belongs to the project (repository) of the current directory. Commands that take `NAME` act on the record that `NAME` resolves to from the current directory (project first, then global); `--global` or `--project` picks a layer explicitly. `--project` outside a repository fails with `no_project` (exit 3).

## Setup

| Command | What it does |
| --- | --- |
| `version [--json]` | Print version, commit and platform. Human: `qbit-vault <version> (<commit>, <os>/<arch>)`. A release build sets both by ldflags; a `go install …@<tag>` build reports the module version, a checkout build `dev` and the first 12 characters of its commit, and a build with neither `dev (unknown, …)`. JSON: `{"ok":true,"version":…,"commit":…,"go":…,"os":…,"arch":…}`. |
| `init [--agents claude-code,codex,pi\|none] [--passphrase] [--passphrase-stdin]` | Full one-shot setup. See INSTALL.md. Idempotent: **every run** creates the vault when it is missing and then registers the hosts, so running it again after installing a new agent (or after a host rewrote its config) repairs the registration and changes nothing else. `--agents` takes a comma-separated list of host names, or `none` to skip host steps (`none` cannot be combined with names; an unknown name is the usage error `unknown agent; available: <names>`, an empty value is `--agents needs host names or 'none'`; all checked before anything is created). Without the flag it registers the hosts it detects on this machine; with it, the named hosts are registered whether or not they are detected. Available hosts: `claude-code` (MCP entry in `~/.claude.json`, hooks and deny rules in `~/.claude/settings.json`, see AGENT_INTEGRATIONS.md), detected by a `~/.claude` directory or a `claude` binary on `PATH`; and `codex` (the `[mcp_servers.qbit-vault]` table in `~/.codex/config.toml`, edited as text, see AGENT_INTEGRATIONS.md), detected by a `~/.codex` directory or a `codex` binary on `PATH`; and `pi` (the `qbit-vault` entry under `mcpServers` in Pi's `mcp.json`, in `$PI_CODING_AGENT_DIR` when that variable is set and `~/.pi/agent` otherwise, see AGENT_INTEGRATIONS.md), detected by that agent directory, a `~/.pi` directory, or a `pi` or `gentle-shell` binary on `PATH`. The Pi extension is not published yet, so `init` prints no install command for it; until a host is detected or named, `init` is vault-only (`--no-extension` does not exist yet). It never reads the environment for values and never asks for a secret. It finishes by running `doctor` (below). **Output**: the vault line, then one line per processed host, then the doctor report. The vault line is `vault initialized at <home> (keychain: <mode>)` for a new vault and `vault already initialized at <home>` otherwise (exit 0). A host line is `host <name>: registered (<steps that wrote a file>)`, `host <name>: up to date`, or `host <name>: failed at <step>`. The doctor report is printed when at least one host was processed or when it found a problem; a plain healthy vault-only run prints just the vault line, as before. When this run registered or changed any host, the human output ends with `Restart your coding agents so they load QBit Vault.` (not in `--json`). With `--json` the object is `{"ok":…,"initialized":…,"home":…,"keychain":…}` (`keychain` only for a new vault), plus `"hosts":[{"name","changed","steps":[…changed step names]}]` and `"doctor":{…}` (same shape as `doctor --json`) under the same condition; `ok` is the doctor's verdict. Exit 1 when the doctor finds a problem. A host step that fails stops that host only (its file is untouched, earlier steps stay recorded), the other hosts still run, and `init` exits 1 with `error: host registration failed: <host> (<step>)[, …]; run 'qbit-vault doctor' for details` (JSON: just the error object, code `host_failed`). A master key that already exists for the vault home (a leftover `key.enc` or keychain entry without a vault) stops it with `a master key already exists for this vault home; run 'qbit-vault doctor'`. `--passphrase` keeps the key in `key.enc` instead of the OS keychain. Without `--passphrase-stdin` the passphrase is asked twice on the controlling terminal (`/dev/tty`, `CONIN$`; input hidden, never read from stdin); a mismatch asks both again, up to 3 times in total, and the third is the usage error `passphrases do not match`; Ctrl-C or end of input is `cancelled` (exit 1), a blank one is `empty passphrase`, and none of them creates anything. With no controlling terminal it is the usage error `no controlling terminal available; use --passphrase-stdin`. `--passphrase-stdin` reads the first line of stdin instead. If creating the vault fails, the key just created is removed. |
| `sync [--agents a,b] [--json]` | Re-apply the registration steps of every host recorded in `state.json` (after an upgrade, a moved binary or a config the user edited), then print the doctor report. Only recorded hosts run: a host that is merely detected is never registered unless `--agents` names it. Idempotent: a run with nothing to change writes no config file, no snapshot and no `state.json`. One line per host, `host <name>: up to date`, `repaired (<steps>)`, `registered (<steps>)` (new via `--agents`), `failed at <step>` or `no adapter in this build; left as is` (the record is kept); `no hosts registered; run 'qbit-vault init'` when there is none. A failed host is `host_failed` (exit 1, as in `init`); any `warn`/`fail` in the report is exit 1. `--json`: `{"ok","hosts":[{"name","status":"up_to_date\|repaired\|registered\|failed\|no_adapter","steps"}],"doctor":{…}}`. Needs a vault; reads no secret. Not vault sync: that is `remote sync` (below). When the vault syncs with a server, the human output ends with `(to sync secrets between devices: qbit-vault remote sync)` (not in `--json`). |
| `doctor [--json]` | Read-only health report: no write, no prompt, no network. Exit 0 healthy, 1 when any check is `warn` or `fail`. Checks, in order: `vault` (state readable, then opened the way `remote status` opens it: `unlocked (keychain: <mode>)`, or `locked (…)` when the key needs a prompt, which is not a problem; `fail` when there is no vault, state.json is damaged or the vault cannot be opened), `permissions` (vault home and files owner-only, else `warn` naming the file), one `host.<name>.<step>` per step of each registered host (`registered`, or `warn`: `config changed since registration; run 'qbit-vault sync'`, `not registered; run 'qbit-vault sync'`; a recorded host this build has no adapter for is `host.<name>` `warn`), and, when the vault syncs, `sync` from the last round's summary in `state.json` (`<server>; <n> devices, <n> conflicts[, push pending]; last round <time>`, `<server>; no sync round yet`, or `warn`: `<n> sync conflicts; run 'qbit-vault remote conflicts'`). Human output is one line per check, `<status padded to 4>  <name padded>  <detail>`, then `healthy`, `1 problem` or `<n> problems`, on stdout. JSON: `{"ok":<healthy>,"checks":[{"name","status":"ok\|warn\|fail","detail"}]}` on stdout in both outcomes. `prompt` names the dialog backend the commands would use, e.g. `prompt: powershell (WSL)` (`powershell`, `osascript`, `zenity` or `kdialog`); it says nothing when the backend is the terminal, and is `warn` when `QBIT_VAULT_PROMPT` names a backend that cannot run. It starts no helper and opens no window. Two more checks speak only when something is wrong, so a healthy report stays short: `audit` (`fail`: `audit chain broken at line <n> (<reason>); run 'qbit-vault audit --verify'`) and `grants` (`warn`: `grants.enc is unreadable or was rolled back; its grants are treated as none`). A drifted or unregistered step now points at `qbit-vault sync`. Hooks for Claude Code are the `host.claude-code.hooks` step; a moved or deleted binary shows up as drift of the steps that hold its path. `doctor` does not check the binary's signature or version. |
| `uninstall [--purge]` | User-only (prompt backend; `not_model_callable` without one; the pre-bash hook denies it in the agent's shell). Asks one yes/no, then reverts every host recorded in `state.json` with the `filemerge` revert rule: the config is restored byte for byte when it is still exactly what we wrote, otherwise only our entries are removed and the user's later edits stay. One line per host listing each step's outcome (`restored`, `stripped`, `deleted`, `absent`, `unchanged`), e.g. `host claude-code: deny restored, hooks stripped, mcp deleted`, then `vault kept at <home>`. A host is forgotten in `state.json` only when its revert succeeded; a failed one (`failed at <step>; kept in state.json`) or one this build has no adapter for is kept, and the command exits 1 with `host_revert_failed`. The vault, its key and the audit log stay (an `uninstall` audit record is appended). `--purge` asks instead to type the word `purge` (visible; anything else, a confirm or a cancel changes nothing), and only if every host reverted deletes the vault home and the key's OS keychain entry (`vault purged: <home>`); it deletes nothing else and refuses a directory that is not a plain vault home (`unsafe_purge`: the user's home or a parent, a root, a symlink). It refuses before asking while the vault syncs (`sync_configured`): run `remote logout` first. `--json`: `{"ok","home","purged","hosts":[{"name","status":"reverted\|failed\|no_adapter","steps":[{"name","outcome"}]}]}`. |
| `tui` | Open the interactive terminal UI (see [TUI](#tui)). Needs a terminal on stdin and stdout; `--json` is a usage error. `qbit-vault` with no arguments opens it too, under the conditions listed there. |
| `update [--check]` | User-only (prompt backend; `not_model_callable`, exit 3, without one; the pre-bash hook denies it in the agent's shell). Brings this binary to the latest stable release. It asks the releases API (`https://api.github.com/repos/qbitdevz/qbit-vault/releases/latest`; `QBIT_VAULT_RELEASES_API` overrides it as for the installers and may name one release or a list, from which the newest published non-draft, non-prerelease is taken) and compares with the running version (a pre-release is older than its release). Up to date: `qbit-vault <version> is up to date`, exit 0, nothing downloaded. Newer: it asks `Update QBit Vault <current> to <latest>?` (default No; a no is `cancelled`, exit 1, and changes nothing), downloads `qbit-vault_<os>_<arch>.tar.gz` (`.zip` on Windows) and `checksums.txt` over HTTPS, checks the archive's SHA-256 against its line in `checksums.txt`, extracts `qbit-vault` (`qbit-vault.exe`), flushes it to disk and swaps it in atomically: POSIX renames the new file over the running one (same directory, mode 0755); Windows renames the running `qbit-vault.exe` to `qbit-vault.exe.old-<8 hex>` and moves the new one in, putting the old back if that fails, and a later `update` removes the old copies. A missing checksum line, a mismatch, a missing binary in the archive or any download error stops with a one-line message (exit 1) and leaves the installed binary byte-identical; the only thing written beside it is a temp file that is removed. When the vault is set up (`state.json` exists) it then runs `sync` of the new binary, so the registrations and the agent skill are those of the new version (skipped with `QBIT_VAULT_NO_SYNC=1`; a `sync` problem is a stderr note and the binary stays updated), and prints `updated qbit-vault <current> -> <latest>; restart your agents so they load the new version`. `--check` only reports `update available: <current> -> <latest>` or `qbit-vault <version> is up to date`, exit 0 either way, with no prompt and no download. `--json` (both forms): `{"ok":true,"current":…,"latest":…,"update_available":bool}`, plus `"updated":true` after a real update. A build that is not a release (`dev`, `+dirty`, a pseudo-version, no version) refuses with the usage error `this build is not a release; install with the one-line installer or 'go install github.com/qbitdevz/qbit-vault/cmd/qbit-vault@latest'` (exit 2); `--check` still reports, treating such a build as older than any release. A binary whose directory is not writable stops with `cannot replace <path>: re-run the install command` before any download or question. Only the GitHub API and the release assets are contacted, over HTTPS (an `http://` override is accepted for a loopback host only); redirects are followed within that rule, with timeouts and size caps. The vault, grants, audit log and sync state are never opened or written and no secret is read. |

## Secrets

| Command | What it does |
| --- | --- |
| `set NAME [--global\|--project] [--stdin] [--description D] [--sensitive] [--binaries gh,git] [--hosts api.github.com] [--grant once\|session\|project] [--from-prompt-token T]` | Store or replace a value. Without `--stdin` it is interactive: inside a repository with neither layer flag it first asks *All projects* or *Only this project (label)* (default all projects), then shows the request (who asks, the secret, the reason `manual entry`, where it is saved, whether the value is new or replaces the saved one) and reads the value from the controlling terminal with echo off (`/dev/tty`, `CONIN$`; never from stdin; nothing is echoed, not even a mask). The terminal takes **one line**: a multi-line paste is refused with the usage error `the input continued after Enter; paste a single line, or use --stdin for multi-line values`, the extra text is discarded from the terminal input queue (flushed, so the shell never sees it and it never reaches history) and nothing is stored; multi-line values need `--stdin`. The same applies to passphrases. Blank input is the usage error `empty value`, input over 64 KiB `value too large`, Ctrl-C or end of input at any question (a hidden read, a numbered menu or a y/N question) is `cancelled`; an unanswered prompt gives up after the **prompt timeout** (below) with `No answer in time; nothing was saved.`, also exit 1 and code `cancelled` (exit 1, stderr `error: cancelled`); none of them writes anything. With no controlling terminal it is the usage error `no controlling terminal available; use --stdin`. Interactive `--grant once\|session\|project` is the proposed scope: after the value a menu offers the scopes this secret and session allow (`once` only for a sensitive one, `project` only inside a repository, `once` and `session` only with `--session`) plus `Save it, don't allow yet`; the preselected entry is the scope given with `--grant` (the user typed it), else `session` (labelled `Session: this agent session, for 12h`) when offered, else the first; choosing one is the confirmation (the grant is audited as `prompt token`); a grant that cannot be made is refused before the value is asked. `--from-prompt-token` is `--stdin` only (usage error `--from-prompt-token needs --stdin`). `--stdin`: read value from stdin (used by hosts). `--grant` also creates a grant for `--session` in the same call (used by the capture flow so first use costs one prompt); because stdin carries the value there is no question to ask, so `--grant` **requires `--from-prompt-token T`** (usage error `--grant requires --from-prompt-token`; `--from-prompt-token` alone is `--from-prompt-token requires --grant`), and the token is checked, and the scope validated (a `sensitive` secret accepts `once` only), **before** anything is stored: a refused grant stores nothing. Replacing the value of an existing secret drops that record's grants (R-API-07). With `--stdin` there is no layer question: inside a repository pass `--global` or `--project`, else usage error `choose --global or --project`; outside one, `set` writes to the global layer. Surrounding whitespace is trimmed, the trimmed value is at most 64 KiB, and a blank value is a usage error (`empty value`) that writes nothing. Replacing a secret keeps the metadata you do not pass again. A name that changes how a command starts (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `DYLD_*`, `BASH_ENV`, `ENV`, `PATH`, `PATHEXT`, `PYTHONSTARTUP`, `NODE_OPTIONS`, `PERL5OPT`, `RUBYOPT`, `COMSPEC` and `PROMPT_COMMAND`) is the usage error `NAME cannot be used as a secret or variable name: it changes how a command starts` (NAME is that variable), checked before anything is asked or read, and nothing is stored. |
| `rm NAME [--global\|--project] [--yes]` | Delete value and all its grants. Without a layer flag it deletes the record `NAME` resolves to. Without `--yes` it asks `Remove NAME (<layer>)? [y/N]` on the controlling terminal; anything but `y`/`yes`, Ctrl-C or end of input is `cancelled` (exit 1) and removes nothing. With no controlling terminal it is the usage error `confirmation required; pass --yes`. `--yes` never asks (for scripts). |
| `mv NAME --to global\|project [--yes]` | Move a secret between global and the current project. Keeps value and metadata, drops its grants, asks before overwriting a same-named secret in the target: `NAME already exists in <layer>; overwrite? [y/N]` on the controlling terminal (a no or cancel is `cancelled`, exit 1, and nothing moves), or, with no controlling terminal, the usage error `NAME already exists in <layer>; pass --yes to overwrite`. `--yes` overwrites without asking. Outside a repository it fails with `no_project`. |
| `list [--layer here\|global\|project\|all] [--json]` | Names and metadata, never values. `here` (default): what resolves from this directory, marking project overrides. `global`: only the global layer. `project`: only this repository's layer (`no_project` outside one). `all`: every layer including other projects. Human output is a table `NAME  LAYER  DESCRIPTION` (`LAYER` is `global` or `project:<label>`; overrides are marked `(overrides global)`); an empty result prints `no secrets`. While sync conflicts exist (REMOTE_SYNC § 7.4) the human output also prints `N sync conflicts; run 'qbit-vault remote conflicts'` on stderr; stdout and `--json` are unchanged. |
| `describe NAME [--global\|--project]` | Metadata, layer and active grants for one secret. `grants` lists the active grants of that record only (a grant on the global `NAME` is not shown on the project `NAME`): `{"scope","session","expires_at"}` each; human output shows `none` or `<scope>, for <session>, until <time>` (`until revoked` for `project`). |
| `edit NAME [--global\|--project] [--description] [--sensitive=true\|false] [--binaries] [--hosts]` | Change metadata, never the value. At least one change flag is required (usage error otherwise). Making a secret `sensitive` drops its `session` and `project` grants (a `once` grant stays) in the same operation; the JSON then carries `grants_dropped`. Other edits keep their grants. |
| `link LABEL [DIR]` | Bind a project layer that has no root on this device (it came from another machine through sync) to the repository root of `DIR` (default the current directory). User-only: confirmed through the prompt backend (`Use the secrets of project <label> in <root>?`), never automatic, and with no prompt backend it is refused with `not_model_callable`; a no is `cancelled`. `DIR` outside a repository is `no_project`. Errors never echo `LABEL`: `no unlinked project layer has that label`, `several unlinked project layers have that label`, `this repository already has a project layer`, `give the label of the project layer to link`. Grants are not carried (there are none on this device yet). Audited as `link`. Human: `linked <label> to <root> (N secrets)`. `list --layer all` marks such layers `(not linked on this device)` (`"unlinked":true` in JSON), and a human `list` in a repository whose origin matches one prints `hint: project secrets "<label>" from another device match this repository; run 'qbit-vault link <label>'` on stderr. |
| `relink OLD_ROOT NEW_ROOT` | Repoint a project layer after moving or re-cloning a repository. `OLD_ROOT` must be an existing project layer (it need not exist on disk); `NEW_ROOT` must be a repository root (contains `.git`, else `no_project`) without a layer of its own. **Grants do not follow the layer:** every grant of the old project layer is dropped (relink can only narrow access) and the user grants again for the new root; the output reports `grants_dropped`. |
| `import --from-env NAME[,NAME…]` / `import --from-file PATH [--names A,B]` `[--global\|--project] [--yes] [--remove-source]` | Explicit, user-run import from the current environment or a dotenv file. Never run by `init`. Prints what it imported by name and offers to unset/remove the source. Give exactly one source (`choose --from-env, --from-file or --from-export`); `--names` and `--remove-source` need `--from-file`. Layer as for `set`: the flag, else global outside a repository, else the question `Where should these secrets live?` (no prompt backend: `choose --global or --project`). Unless `--yes` it asks `Import A, B from <the environment\|the dotenv file> into <layer>? Existing secrets with these names are replaced.` (no prompt backend: `confirmation required; pass --yes`; a no is `cancelled`). Every value is trimmed like `set`, at most 64 KiB (`NAME is too large`), and all are stored in one locked write: a replaced secret keeps its metadata and loses its grants. Environment: a missing or empty variable is `NAME is not set or empty in the environment`; afterwards stderr says `hint: unset A B in your shell; qbit-vault cannot change the environment of the shell that started it`. A name that changes how a child starts (the list under `exec`) is refused before anything is asked or stored, with the same usage error as `set` (`NAME cannot be used as a secret or variable name: it changes how a command starts`, exit 2); only names that would be imported count (`--names` can leave one out). Dotenv (at most 1 MiB, else `dotenv file too large`; unreadable: `cannot read the dotenv file`): `KEY=VALUE` lines, `#` comments, optional `export `, single quotes literal, double quotes with `\n \r \t \" \\` escapes, both may span lines, unquoted values end at a ` #` comment; a line with no `=`, an invalid name or an empty value is skipped and counted (`note: skipped N lines (invalid name, no '=', or empty value)` on stderr); a syntax error is `the dotenv file has an error at line N: unterminated quote` (or `text after the closing quote`), never quoting the file; the last of repeated names wins; a `--names` entry the file lacks is `NAME is not set in the file`; nothing left is `nothing to import`. `--remove-source` deletes the file afterwards; interactively the user is asked `Delete the dotenv file now that its values are in the vault?`. Audited as `capture` with `reason` `import from env` or `import from file`. Human: `imported N secrets into <layer>: A, B` plus ` (replaced: B)`. |
| `export FILE [--force]` | Write an encrypted, portable copy of the whole vault to FILE: the offline backup that needs no server, no sync and no account (format: STORAGE.md § Export file format). FILE that already exists is refused before any question (`FILE exists; pass --force to overwrite`); `--force` replaces it atomically. An empty vault is `the vault is empty; nothing to export`. It asks a new **export passphrase** twice through the prompt backend (labelled `Export passphrase (protects this backup file)` and `Type the export passphrase again`, so it is not mistaken for the vault passphrase; masked; never from an argument, the environment, stdin or a file; no prompt backend: the usage error `no controlling terminal available`): fewer than 12 characters is `the export passphrase must be at least 12 characters`, two different entries are asked again (3 tries in total, then `passphrases do not match`), a cancel or a timeout `cancelled` (exit 1); nothing is written in any of these cases. The file is written owner-only, atomically (temp file in the same directory, fsync, rename), and holds every layer (global and each project layer with its root and label) and every secret with its value and metadata. Not included: grants, prompt tokens, the audit log, backups, keychain material, sync state, device keys. It opens the vault like any command (a passphrase-mode vault asks its own passphrase first), makes no network call and works whether or not the vault syncs. Project layers synced from another device that have no root here are not exported (`note: N secrets in project layers not linked on this device were not exported` on stderr); when those are all the vault holds, it is the usage error `nothing to export on this device: N secrets are in project layers not linked here; run 'qbit-vault link' or export from the device that has them`, asked before any passphrase. An export that would be larger than 64 MiB is the usage error `the export would be larger than 64 MiB and could not be imported back`, and nothing is written. Audited as `export` with the count only (`N secrets`). Human: `exported N secrets (global: G, projects: P) to FILE`, then on stderr `keep the file and its passphrase in different places; anyone with both can read every secret`. |
| `import --from-export FILE [--yes]` | Restore from a file written by `export`: a third source next to `--from-env` and `--from-file` (exactly one; `--names` and `--remove-source` are usage errors with it as before, and `--global` and `--project` are `--global and --project do not apply to --from-export; every secret returns to its own layer`). Unreadable file: `cannot read the export file`. It asks the export passphrase once through the prompt backend (labelled `Passphrase of the export file`; no prompt backend: the usage error `no controlling terminal available`); a wrong passphrase, a changed byte, a truncated file or an unknown format are all `cannot open the export: wrong passphrase or damaged file` (exit 1) and write nothing. The export is **merged** into the vault: every secret returns to its own layer (global to global; a project layer to the project with the same root path, created if absent, its label kept if present). A secret whose name does not exist in that layer is added; one that does is replaced whole (the export is the source of truth: nothing is kept from the old one, and its grants are dropped). Secrets of the vault that the export does not name stay untouched, grants included. Grants are never imported. Unless `--yes` it first asks `Import N secrets from the export? These replace existing ones: A, B` (a clash in a project layer reads `NAME (project LABEL)`; just `Import N secrets from the export?` when nothing is replaced; a backend that cannot ask the question: `confirmation required; pass --yes`; a no is `cancelled`). Everything is stored in one locked write, so it works on the empty vault that `init` just made on a new machine. Audited as `capture` with `reason` `import from export`. Human: `imported N secrets from the export` plus ` (replaced: A, B)`. |
| `rekey` | Rotate the master key, crash-safe (STORAGE.md § Master key): the new key is staged first (keychain account `master:next:<id>`, or `key.next.enc` under the same passphrase), then `vault.enc` (snapshotted), `grants.enc` and `keys/retired.enc` are re-sealed with it and the old key is retired, then the new key replaces the old one. In passphrase mode the passphrase is asked to wrap the new key and must be the current one (a wrong one is `vault_locked`, exit 4, and nothing changes); changing the passphrase is not part of `rekey`. A rolled-back or corrupt vault is refused (`vault_corrupt`) before anything changes. If the process dies midway, the next command that opens the vault finishes the rekey and prints `warning: an interrupted rekey was finished` (audit `warning`). Grants and backups survive (old backups open through the retired key). Audited as `rekey` with the keychain mode. Human: `master key rotated (keychain: <mode>)`. **With sync enabled** it is user-only (it shows the new recovery key out of band; a device the server lists that this vault's roster does not know is revoked in the same call, with `unknown device <id> was revoked` on stderr; with no prompt backend it is `not_model_callable`), asks one confirmation, and runs REMOTE_SYNC § 4.5 steps 3-6 without revoking anyone: one account-wide rotation to generation g+1, every device switches on its next round, the recovery key is replaced. Human: `master key rotated (keychain: <mode>); the account is now generation N`; `--json` gains `"remote":"synced"`. |
| `lock` / `unlock` | Passphrase mode: drop / refresh the cached master key. `lock` reads no key and asks nothing: in passphrase mode it deletes the unlock cache (`vault locked: the cached master key was removed`); in keychain mode there is nothing to drop (`nothing to lock: the master key is in the OS keychain (<mode>)`). `unlock` always asks the passphrase (it does not trust a cached key), checks that the key opens the vault and caches it where a memory-backed cache exists (`vault unlocked until <time>`); without one it says `passphrase ok; this platform has no unlock cache, so the passphrase is asked on each use`. In keychain mode it only checks the key (`unlocked: the master key is in the OS keychain (<mode>)`). A wrong passphrase is `vault_locked` (exit 4) and leaves the cache as it was; no prompt backend is the usage error `no controlling terminal available`. Neither writes an audit record. **Agent calls** (MCP `secret_request`, `secret_manage`; the host transport's `request`, `manage`, `grant`, `revoke`) that find a passphrase-mode vault locked do not send the user to this command: they ask the passphrase out of band through the prompt backend, in a dialog headed `Vault passphrase` whose text names the requester and the secret (`<Requester> wants to use <NAME>. Unlock the vault to continue.`, with ` (<layer>)` after the name when the call states one; `<Requester> needs the vault. Unlock it to continue.` with no name), through the same one-dialog-at-a-time gate and the call's own cancel as every other dialog. A right passphrase unlocks with the same cache and time as `unlock` and the call goes on to its own permission question (unlocking never grants); a wrong one is the retryable `vault_locked` (the agent calls again); a cancel is `user_declined`, or the retryable `internal` cancel when the client itself gave up; no prompt backend is `vault_locked`. The unlock is audited as one `unlock` record (`by` `agent`, the session, the names, `detail` the requester; never the passphrase). `secret_exec` and `secret_list` never ask: their `vault_locked` message tells the agent to call `secret_request`. Hooks never ask (below). `QBIT_VAULT_NO_PROMPT_UNLOCK=1` turns the agent dialog off (agent calls answer `vault_locked`, as before); commands the user runs are not affected. |
| `restore --list` / `restore --from ID [--yes]` | Restore the vault from an encrypted backup. Give exactly one of `--list` or `--from` (usage error `choose --list or --from`). `--list` needs no key: one line per snapshot, newest first, `<ID>  <files>` (`no backups` when there are none). `--from ID` takes an id from that list (anything else is `invalid backup id`, never echoed; a valid id with no snapshot is `no backup <ID>`), asks `Restore the vault from <ID>? The current vault is backed up first. [y/N]` unless `--yes` (no prompt backend: `confirmation required; pass --yes`; a no is `cancelled`), opens the snapshot's `vault.enc` with the current key or a retired one (`keys/retired.enc`), and saves it as the next write: the current pair is snapshotted first and the rollback counter moves forward. It works when the live vault is corrupt or rolled back, and unlocks with the snapshot's vault id when the live `state.json` is unreadable. A snapshot no known key opens is `vault_corrupt` (`backup cannot be opened with the current or a retired key`) and changes nothing. Grants are kept (they bind record ids, which restore keeps). Audited as `restore` with the backup id. Human: `restored the vault from <ID> (the previous state was backed up first)`. |

**Several values in one call (*planned*, roadmap slice 4.3 with the Pi extension's capture, together with `prompt --field`; neither flag is in the binary yet; the MCP path does not need it, the broker stores multi-field captures itself).** `set --stdin --fields A,B,C [--kinds secret,text,text] --grant S --from-prompt-token T` reads one JSON object `{"A":"…","B":"…","C":"…"}` from stdin and stores every field in one locked operation, all-or-nothing (a missing, extra or blank field stores nothing), then creates one grant per record with a token issued for exactly those names. It is how a host stores the values of a multi-field capture (CONTRACT `request` with `fields`). `--kinds` defaults every field to `secret`.

## Remote sync

> **Two commands share the word "sync".** `qbit-vault sync` (Setup) re-applies the coding-agent registrations; `qbit-vault remote sync` syncs secrets between devices. They are not the same and neither renames the other.

Opt-in multi-device sync through `qbit-vault-server` (`REMOTE_SYNC.md`). Commands marked *user-only* ask every question and show every code through the prompt backend (native dialog, else the controlling terminal), accept no code, key or invite as argument or on stdin, never print the recovery key or a confirmation code on stdout, stderr or `--json`, and are refused with `not_model_callable` when no prompt backend is available.

| Command | What it does |
| --- | --- |
| `remote register --server URL [--ca-file PATH]` | *User-only.* Register this vault on the server as the first device: asks the invite code, confirms, uploads the vault sealed on this device, then shows the recovery key and asks for its last four characters (a wrong answer shows the key again, until it is right or you cancel). The device's state is saved before the key is shown, so cancelling there leaves the account registered, `remote status` warns `recovery key not confirmed`, and the message says `run 'qbit-vault remote recovery-key --rotate' to get a new recovery key`. If the device cannot save its state after the server created the account, the device is removed from the server again and the command fails with code `internal`, `the account was created on the server but this device could not save its sync state; run 'qbit-vault remote register' again with a new invite code` (the recovery key is not shown; the empty account stays on the server). `https://` only, except loopback `http://`; a refused invite is `remote_auth`. Needs an initialized vault and a prompt backend that can show text, else `not_model_callable`. |
| `remote join --server URL [--recovery] [--ca-file PATH]` | *User-only.* Add this machine. Default: pairing; prints the pairing code (`XXXX-XXXX-XXXX-XXXX`, safe to show) and waits up to 10 minutes for `remote approve` on another device, then asks the confirmation code shown there (its own question, headed `Confirmation code`). `--recovery`: asks the recovery key instead. A non-empty local vault is merged into the account after a confirmation that names how many secrets will be added. Needs an initialized vault (`init` first): the account master key replaces the local one the way `rekey` does (the old key is retired). With `--json` the pairing code goes to stderr so stdout stays one object. The joining device starts with the version floor of the device that approved it, so an older version served on its first round is `remote_rollback`. A device the account revoked joins again as a new device: this vault takes a new device id and its project roots move to it before the account key replaces the local one (REMOTE_SYNC § 4.5); the old id stays revoked. A wrong confirmation code, an expired pairing or a code the server cannot vouch for is `pairing_failed` and leaves the vault as it was; an unknown recovery key is `remote_auth`. Failures after the account key replaced the local one: if this device cannot save its sync state, it is removed from the server again and the command fails with code `internal`, `the vault now uses the account key but this device could not save its sync state; run 'qbit-vault remote join --recovery' to finish` (the roster of the approving device still lists the id, so a second pairing is refused; the recovery key finishes it); if the first sync round fails, the state is saved and the error keeps its own code (`remote_unreachable`, `internal`, `remote_rollback`, …) with the message `this device joined the account but the first sync did not finish; run 'qbit-vault remote sync'`. |
| `remote approve` | *User-only.* On a device that already syncs: asks the pairing code, verifies it against the new device's keys (`pairing_failed` when they do not fingerprint to it), then asks the device name (Enter takes `device <n>`, n = devices in the roster + 1); that dialog says the device will be able to read every secret and is the consent, so Cancel refuses and nothing is sent. Then it shows the confirmation code to type on the new device. Audited as `approved <device id>`. Once the server accepted the approval the confirmation code is always shown; if this vault then cannot write the new device into its roster, stderr says `warning: the new device was approved on the server but this vault could not record it in the roster; check 'qbit-vault remote devices'` and the command still exits 0. |
| `remote sync [--json]` | Run one sync round now (pull, merge, push). Prints `synced (version N)`, `up to date (version N)` or `pending: <reason>` (`--json`: `{"ok":true,"result":"synced\|up_to_date\|pending","version":N,"reason":"…"}`). With `QBIT_VAULT_NO_REMOTE=1` it only marks the push pending. An unreachable server is `remote_unreachable` (exit 1) and marks the push pending; a version older than one already seen is `remote_rollback` (exit 5). A key generation newer than this device's first runs the key swap of REMOTE_SYNC § 4.5 (the new key is accepted only from a key envelope issued by a non-revoked device of this device's own roster, with a valid signature and AAD, that opens the server's current vault; otherwise `remote_auth`, `the new account key could not be verified`, and the device keeps its key); an older generation is `remote_rollback`. When the merge drops conflicts older than 30 days or beyond the limit of 100, the round audits one `warning` (`<n> old conflict(s) discarded`) and `remote sync` prints `<n> old conflict(s) were discarded; the current values are unchanged` on stderr (the `--json` object is unchanged; automatic rounds only audit). A round that finds a device this device did not know, added by pairing or recovery, appends an audit `warning` (`device added: <label> via pairing\|recovery`). A server that answers `device_revoked` turns sync off on this device (`remote/` and `state.json.remote` removed; vault, key and backups stay), prints `this device was revoked; sync is now off here and the local vault is intact` and exits 1 with code `device_revoked`; in the automatic rounds of other commands the same line is a `warning:` and the command still exits 0. |
| `remote status [--json]` | Server, account, device, generation, version, last sync, pending push, conflicts, devices, anchor state. Read-only: it never prompts, never finishes an interrupted rekey and makes no network call (it reads `state.json` and the encrypted roster). When the master key is not available without a prompt (passphrase mode with no unlock cache) or the vault waits for an interrupted rekey, it still shows everything `state.json` holds: every sync round records its counts there (conflicts, live devices, devices added by recovery; counts only, never a name or label), so `conflicts` and `devices` show those counts followed by `(as of the last sync)` and the warnings come from them (`N device(s) added by recovery`, without the label); `--json` then has `"locked":true` and `"counts_from":"last_sync"`. A vault that has not synced since this was added prints `locked (run 'qbit-vault unlock')` for both, with `null` in `--json` (the device label is omitted either way). `"locked":false` otherwise. Exits 1 with `warning:` lines on stderr (`warnings` in `--json`) when a push is pending, conflicts exist, the recovery key was never confirmed, or a device was added by recovery. `anchor` is the time (UTC, RFC 3339) of the last audit anchor this device uploaded (REMOTE_SYNC § 8), or `none uploaded`. |
| `remote devices [--json]` | The roster, read-only: one line per device with id, label, `added:` (pairing, recovery, register), `last sync:` when known, `last seen:` (the server's last-seen time, asked best effort; offline or with `QBIT_VAULT_NO_REMOTE=1` it is left out) and `revoked:`; this device is marked. A device that only pulls shows `last seen` and no `last sync`. `--json` rows keep their fields and add `last_seen` when known. |
| `remote revoke-device ID` | *User-only.* Revoke a device and rotate the master key and the recovery key. Refused with a usage error, before any prompt, for this device (`this device cannot revoke itself; use 'qbit-vault remote logout'`), an id that is not in the roster, or one already revoked. Confirms out of band (label, last sync), pulls and merges, then one `POST /v1/rekey` (a 409 restarts from the pull, at most 3 tries, then `the server changed while rotating the key; try again` and nothing changes here), re-seals the local files with the new key through the staged `rekey` path, and shows the new recovery key with the last-four confirmation of `register` (a wrong answer shows the key again; cancelling that screen leaves the account rotated, `remote status` warning `recovery key not confirmed`, and the message says `run 'qbit-vault remote recovery-key --rotate' to get a new recovery key`). A device the server lists that the roster does not know (an interrupted approve) does not block it: it is revoked too, with `unknown device <id> was revoked` on stderr and an audit `device revoked <id>`. The revoked device can join again, as a new device with a new id (REMOTE_SYNC § 4.5). Audited as `remote` `device revoked <id>` and `rekey` `remote generation N`. Human: `revoked <label> (<id>); the account key is now generation N`; `--json`: `{"ok":true,"revoked":"<id>","generation":N}`. |
| `remote recovery-key --rotate` | *User-only.* Replace the recovery key; the old one stops working. The account key and the vault stay as they are (`PUT /v1/recovery` at the current generation); when the account key may also be exposed, run `rekey`, which replaces both. Shows the new key with the last-four confirmation of `register`, which clears `recovery key not confirmed` (a wrong answer shows the key again; a cancel keeps the warning and the message says `run 'qbit-vault remote recovery-key --rotate' to get a new recovery key`). Without `--rotate` it is a usage error. Audited as `remote` `recovery key rotated`. Human: `recovery key rotated`; `--json`: `{"ok":true,"rotated":true}`. |
| `remote conflicts [--json]` | Records whose other version was kept after a double edit: name, layer, when it lost, and the label of the device that won (from the roster; `unknown device` when it is not there). Read-only and offline: no prompt, no request, never a value, description or any other field of the record. Human: `NAME  global\|project:<label>  kept edit\|deletion lost at <time> to <device>`, or `no sync conflicts`. `--json`: `{"ok":true,"conflicts":[{"name","layer":"global\|project","project"?,"lost_at","winner","deleted"?}]}`, newest loss first. |
| `remote resolve NAME [--global\|--project] --keep current\|conflict` | *User-only.* `--keep current` keeps the record as it is and discards every kept version of it; `--keep conflict` swaps: the kept version becomes the record (fresh clock and record id, so no grant of the replaced record applies) and the replaced record becomes the kept version (a kept deletion deletes the record; run `--keep current` afterwards to end the conflict). Without a layer flag the name must have a kept version in exactly one layer. One confirmation out of band; the result is pushed like any change (`"remote"` in `--json`, which is `{"ok":true,"name","layer","keep","remote"?}`) and audited as `remote` `conflict resolved (keep X)` with the name. Fixed messages, none echoing the name: a name with no kept version is `no sync conflict for that name` (code `not_found`, exit 1); a name kept in several layers is the usage error `several layers hold a conflict for that name; choose --global or --project`; several kept versions of one record make `--keep conflict` the usage error `more than one version was kept for that name; use --keep current to discard them`; an unlinked project layer is `not_found`. `--keep` missing or other than `current`/`conflict` is a usage error; no prompt backend is `not_model_callable`; a cancel changes nothing. |
| `remote history [--json]` | The server's last 10 versions, newest first: version, label of the device that wrote it (from the roster; `unknown device` otherwise) and the time the server stored it. Read-only, needs the server (`remote_unreachable` otherwise), no prompt. Human: `N  <device>  <time>`; `--json`: `{"ok":true,"versions":[{"version","device","at"}]}`. |
| `remote restore --version N` | *User-only.* Make the records of the vault equal to those of server version N. It downloads version N and verifies its AEAD and AAD (this account, this generation, version N), confirms out of band (version, writer, time) and only then runs a sync round (so records from other devices are replaced too, and anything pending is pushed) and writes the difference as **new** changes; until the confirmation it changes nothing locally or on the server, so a cancel leaves a pending change pending. A version sealed under a newer account key than this device's is refused with `the account key changed since the last sync; run 'qbit-vault remote sync', then try again`. The difference is written as **new** changes: a record that differs or is missing gets the stored content with a fresh clock and a fresh record id (so it wins over the current one everywhere and old grants do not apply), a record N lacks is removed and leaves a tombstone, an identical record is left alone. The device roster, the kept conflicts and the grants are not restored (a revoked device stays revoked). The replaced state stays in the local backups (the normal snapshot) and the result is pushed like an edit. Human: `restored version N (K records changed)`; `--json`: `{"ok":true,"restored":N,"changed":K,"remote":"synced\|pending"}`; audited as `remote` `restored version N`. `--version` missing, not a positive number: usage error; a version the server no longer keeps: `restore_unavailable` (`that version is not on the server; run 'qbit-vault remote history'`); a version sealed under an older account key (before a `rekey` or revocation) cannot be opened with the current key: `restore_unavailable` (`that version was sealed under an older account key and cannot be restored`); a blob that fails AEAD or AAD, or is not version N: `remote_auth` (`the requested version could not be verified`). All leave the vault unchanged. |
| `remote logout` | *User-only.* Stop syncing on this device; the local vault and key stay. |

With sync enabled, every command that changes the vault pushes afterwards (5 s budget) and commands that read it for a person or the agent pull first when the last pull is older than 60 s (2 s budget); `exec`, `grant`, `revoke`, `grants` and `audit` never use the network. A push that could not reach the server prints `warning: not synced (server unreachable); will retry` on stderr and the change stays committed locally (exit 0); a push that lost to another device three times in a row prints `warning: not synced (the server changed while syncing); will retry` instead; `--json` success objects of `set`, `rm`, `edit`, `mv`, `relink`, `link`, `import` and `restore` gain `"remote":"synced"|"pending"`, only when the vault syncs (they are unchanged otherwise; the broker's `manage` response is pinned by the contract and has no such field). A round the server's answer makes unsafe (`remote_rollback`, a refused verification, a refused device) is never reported as an outage: the change stays local, the push stays pending, and stderr says `warning: not synced (<code>); the change is kept on this device; run 'qbit-vault remote status'`, also on a read; the command still exits 0. A failed pull before a read is silent when the server is unreachable. The 5 s push budget, the 2 s pull budget and the 60 s pull interval are fixed for now (no `config.yaml` loader yet). `rekey` with sync enabled rotates the account key (see its row). `audit --verify` also checks the server's anchors (`--offline` skips them; a new reason `anchor_mismatch`; see its row).

## Grants

| Command | What it does |
| --- | --- |
| `grant NAME [--global\|--project] --scope once\|session\|project [--ttl 12h] [--from-prompt-token T]` | Grant the record `NAME` resolves to (or the layer named by the flag) after an explicit confirmation. `once` and `session` need `--session` (usage error otherwise); `project` binds to the repository root of the record and needs no session; for a global secret it binds to the repository the command runs in (exactly that one, not a repository nested in it) and is refused outside one (`project scope needs a repository: run it inside one`) or with `--from-prompt-token`. `--ttl` (session scope only, 1m to 24h, default 12h) is a usage error elsewhere or out of range. A `sensitive` secret accepts `once` only, and `project` scope on a global record has no project to bind to: both are refused as `scope_not_allowed` before any question is asked (the second with the message `project scope needs a project secret`). Confirmation (L5): with `--from-prompt-token` the token must be valid for exactly this name, layer, scope, session and TTL (an omitted `--ttl` means the 12h default, so `--ttl 12h` and no `--ttl` are the same binding; a different `--ttl` is refused and burns the token), and for this record when the token was issued for one; otherwise the question `Grant NAME (<layer>) to <session or "this project">, scope <scope>? The `grant` audit record is written **before** the grant is stored; if it cannot be written the grant is not created (refusal `internal`). A repeat grant replaces the identical one. Human: `granted NAME (<layer>): <scope>, for <session>, until <time>` (`until revoked` for `project`). |
| `revoke NAME [--global\|--project] \| --all \| --session-only` | Revoke grants; no confirmation (it only narrows access) and effective for the next check (R-GRANT-06). | `grants [--json]` | Active grants (expired and used `once` grants are purged first): name, layer, scope, session, expiry and time remaining. Human output is a table `NAME  LAYER  SCOPE  SESSION  EXPIRES  REMAINING` (`-` where it does not apply), or `no active grants`. |

### Run a command with a secret by hand

```
qbit-vault set DEMO_TOKEN --global                                   # hidden prompt
qbit-vault grant DEMO_TOKEN --session demo --scope once              # asks you to confirm
qbit-vault exec --session demo --secret DEMO_TOKEN -- sh -c 'printf "%s\n" "${#DEMO_TOKEN}"'
```

The last line runs the command with the value in that one process and prints its length (the value itself would come back as `[REDACTED:DEMO_TOKEN]`). The `once` grant is spent by that run; run `grant` again for the next one.

### Manual entry (no agent involved)

```
qbit-vault set GITHUB_TOKEN --global       # hidden prompt, available everywhere
cd ~/code/shop-api
qbit-vault set DATABASE_URL                 # asks: All projects or Only this project (shop-api)?
```

With Claude Code, Codex or Pi through MCP, run it in any other terminal (the `/vault set` command of the planned Pi extension is not built). The terminal prompt reads the controlling terminal, not stdin, so a pipe cannot answer it; with a desktop session the prompt is a native dialog, not the terminal. When there is no controlling terminal (for example when launched by a host's shell escape without one) `set` fails with `no controlling terminal available; use --stdin`; on a machine with a desktop session the native dialog opens instead of the terminal (`AGENT_INTEGRATIONS.md` § Native capture dialog), so that case is rare.

## TUI

```
qbit-vault tui
qbit-vault            # no arguments: the same, only for a person at a terminal
```

An interactive app for the things you do by hand: first-run setup, secrets, grants, hosts, the audit log, sync status and the doctor report. It is a front end over the commands in this document: each action below runs the command shown, in-process, with the same `--home`, snapshots, atomic writes and audit records. `--home` is honored. It adds no new capability.

**When it opens.**

| Invocation | Result |
| --- | --- |
| `qbit-vault tui` on a terminal | Opens the TUI. |
| `qbit-vault tui` without a terminal on both stdin and stdout | Usage error (exit 2): `the TUI needs an interactive terminal (stdin and stdout must be terminals)`. |
| `qbit-vault tui --json` | Usage error: `the TUI does not support --json`. |
| `qbit-vault` with no arguments, stdin and stdout both terminals, no `--json`, `QBIT_VAULT_NO_TUI` not `1` | Opens the TUI. |
| `qbit-vault` with no arguments in any other case | Unchanged: prints the help (`--json` still gives the usage error `no command given`). Scripts and pipes never see the TUI. |

`QBIT_VAULT_NO_TUI=1` only affects the no-arguments shortcut; `qbit-vault tui` still opens. An unexpected failure of the UI itself prints `the TUI stopped unexpectedly` (exit 1) with no further text.

**First run.** With no vault at `--home` the TUI shows a splash, then a four-step wizard: vault location, key storage (OS keychain, or a passphrase), which detected hosts to register (claude-code, codex, pi), and a review. Nothing is written until you confirm the review; applying runs `init --agents <chosen|none> [--passphrase]`. With a passphrase the TUI suspends and `init` asks for it in the prompt backend. The wizard takes no text input and never asks for a secret. When it finishes it offers to add a first secret.

**Security rules.**

- No secret value is ever shown, and the UI process never holds one. The detail pane shows `••••••••  never shown`. The data the screens receive has no field that can carry a value.
- A value, and a passphrase, are typed only in the prompt backend (native dialog or hidden terminal prompt) while the TUI is suspended, the same prompt `set` and `unlock` use. The add form has no value field; it warns not to paste a secret into the description. The TUI text inputs are only the secret name and the description.
- Grants are revoke-only. No key or code path in the TUI creates or approves a grant (AGENTS.md invariant 6); `set` is never run with `--grant`. Grants are approved in the dialog an agent's request opens.
- Pairing codes, confirmation codes and recovery keys are never shown or read by the TUI.
- While the TUI is showing, the in-TUI commands run in a no-prompt mode: a passphrase vault with no unlock cache is reported as locked (offer `u`) instead of drawing a passphrase prompt over the screen. Only the commands the TUI suspends for (`set`, `unlock`, and `init --passphrase`) can prompt.
- `edit` and `rm` from the TUI keep the CLI's behavior of pushing to a linked sync server afterwards.

**Colors.** `--no-color` (or `NO_COLOR`) removes every color from the screens and shows the plain wordmark instead of the mark. Otherwise the TUI uses 24-bit color when it looks supported (always on Windows; elsewhere when `COLORTERM` is `truecolor` or `24bit`) and falls back to 256 colors, with a solid selection color instead of the gradient.

## Exec

```
qbit-vault exec --session S --secret [ENV=]NAME [--secret …] [--timeout 10m] [--shell auto|sh|bash|cmd|pwsh] [--cwd DIR] [--stream] -- <command…>
```

- Each `--secret NAME` injects vault secret `NAME` as env var `NAME`; `--secret GH_TOKEN=GITHUB_TOKEN` injects `GITHUB_TOKEN`'s value as `GH_TOKEN`.
- `--stream`: stdout/stderr forwarded as redacted chunks as they arrive (NDJSON `{"stream":"stdout","chunk":"…"}` with `--json`, raw otherwise), final record carries `exit_code`.
- **Command.** The words after `--` become one command string for the shell. A single word is the command as is. With several, each word that holds a space, tab or line break (or is empty) is quoted for the effective shell so it stays one word (`'…'` for `sh`/`bash`; `'…'` for `pwsh`, where a single quote, including the typographic `‘ ’ ‚ ‛` that PowerShell reads as one, is doubled; `"…"` for `cmd`); words without blanks stay verbatim, so `|`, `&&`, `>file` and `$NAME` still act as shell syntax. So `exec … -- sh -c 'printf "%s" "${#T}"'` runs that script, not `sh -c printf …`. At most 16 `--secret` flags; `--timeout` between 1s and 1h; the command is 1 to 16384 bytes. Known `cmd` limits: a word that holds a blank and also a `"` is left unquoted (cmd has no escape for it that survives `/s /c`), so it splits at its blanks; and `%VAR%` inside the quotes is still expanded by cmd.
- **Shell.** `auto` is `/bin/sh -c` on POSIX; on Windows it is `bash -c` with Git for Windows' bash, else `cmd /d /s /c`. `sh`, `bash`, `cmd` and `pwsh` force one; an unavailable shell is a usage error. **Windows and WSL.** `bash` and `sh` never resolve to the WSL launcher (`System32\bash.exe`, the `WindowsApps` alias): the shell is the first `bash.exe`/`sh.exe` on `PATH` outside those directories, else Git for Windows' `bin\bash.exe`/`bin\sh.exe`, found from `git.exe` on `PATH` (Git's installer puts only its `cmd` directory there) or under `Program Files\Git` and `%LocalAppData%\Programs\Git`. The child's `PATH` also gets that `bin` directory first, so a bare `bash` or `sh` inside the command, under any shell, runs Git's. With no Git for Windows, a command that names a bare `bash` or `sh` is refused before anything is claimed or started, with the fixed message `bash and sh need Git for Windows, which was not found; WSL is not used (name its bash by absolute path to use it)` (refusal `internal`); an absolute path is the user's explicit choice and is not second-guessed.
- **Variables that change how a child starts.** `exec` refuses to inject a secret under `LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `DYLD_*`, `BASH_ENV`, `ENV`, `PATH`, `PATHEXT`, `PYTHONSTARTUP`, `NODE_OPTIONS`, `PERL5OPT`, `RUBYOPT`, `COMSPEC` and `PROMPT_COMMAND` (the `ENV` of `--secret ENV=NAME`; the lookup is case-insensitive) with the usage error `ENV cannot be used as a secret or variable name: it changes how a command starts` (exit 2), before any grant is looked at: nothing is claimed, audited as `exec` or started. Such a value would steer the child (a library to load, a startup file to run), not feed it.
- **Order of checks.** (1) resolve every secret from the working directory (`--cwd`, default the current one); (2) grants, looking only; (3) dump-command guard (`dump_command`) over the injected variable names; (4) binary allowlist over every pipeline segment (`scope_binary`); (5) hosts advisory (the audit record notes `hosts warning`, the run goes on); (6) claim `once` grants and append the `started` audit record, fail-closed; (7) run. Any refusal runs nothing.
- **Grant lookup.** `exec` and the broker's `list` evaluate grants for the same directory (the repository root when there is one) with the same predicate. When a grant exists but does not apply (a project grant approved in another repository, or a grant of an earlier value), the `grant_required` message says `NAME has a project grant for another directory; call secret_request` (or `…has a grant for an earlier value of it…`); the listing shows `"grant":null` plus `"grant_note"`.
- **`once` grants.** A `once` grant is spent by a child that starts. Steps 1 to 5, a bad flag, a missing shell and any failure to create the process leave it usable: step 6 claims it atomically under the grants lock (so two execs, even concurrent ones, cannot both use one grant; while a claim is held, another exec of that session is refused `grant_required`), and if the process turns out never to have started the claim is given back and the audit gets a `finished` record with `outcome: error`, `detail: not started` and no exit code. A child that starts and exits non-zero, times out or is interrupted keeps the grant spent. A crash between claim and start leaves it spent (the safe side).
- **Dump guard.** One shape that cannot put the value on the output is not a dump: `${#NAME}`, the POSIX length expansion (`exec … -- sh -c 'printf "%s" "${#T}"'` prints the length). Everything else that names an injected value in a dump position stays refused, including `printf '%s' "$T" | wc -c`, `echo $T | wc -c`, PowerShell `$env:T.Length` and any digest (`| sha256sum`). A first version allowed counter pipes and the PowerShell `.Length` form; two independent reviews found commands it let through that print the value (`set -x;` before the pipe, a function named `wc`, `printf '%d'` printing the value on stderr, `Write-Host a$env:T.Length`), so it was withdrawn: a guard that reads text cannot see how the shell will run it. Output redaction stays the real control. The guard reads the script of a shell called with options before `-c` (`bash -o pipefail -c …`, `sh --login -c …`, `bash -O extglob -c …`, `bash --rcfile FILE -c …`), and it refuses `pwsh`/`powershell` with an encoded command (`-e`, `-ec`, `-enc`, `-EncodedCommand`, any case, `-`, `/` or a typographic dash, `-e:VALUE` too) as `dump_command`, because the base64 script cannot be inspected; options that take a value (`-ExecutionPolicy Bypass`, `-WorkingDirectory /f`, `-ep:Bypass`) are skipped with their value, so none of them hides it.
- **Environment.** The child gets the parent environment minus every variable named like a vault secret (case-insensitive on Windows), plus the granted values. The parent is never modified. The child inherits stdin.
- **Output.** Human mode streams the child's redacted stdout/stderr to ours. `--json` prints one object `{"ok":true,"exit_code":N,"stdout":"…","stderr":"…","duration_ms":N,"redactions":N,"truncated":bool}`; each stream is capped at 1 MiB keeping the tail. `--json --stream` prints NDJSON: `{"stream":"stdout|stderr","chunk":"…"}` lines as output arrives, then a final `{"exit_code":N,"duration_ms":N,"redactions":N}`.
- **Timeout.** On expiry the process tree is killed: on POSIX the child's process group (a descendant that started its own session or group is not reached), on Windows a job object that holds the child and everything it starts and the refusal `timeout` (exit 3) is returned; with `--json` it carries `partial: {stdout, stderr}`, in human mode the partial stdout was already streamed. SIGINT/SIGTERM kill the tree and exit 130.
- **Wrapper flags and allowlists.** Wrappers (`sudo`, `env`, `timeout`, `nice`, `strace`, `xargs`, ...) are resolved with an explicit table of known flags. A flag outside the table, or a short-flag cluster whose letters are not all known, is ambiguous and the command is refused with `scope_binary` when an injected secret has a `binaries` list. Write such commands without the unusual flags, or call the program directly.
- **`--shell cmd` / `pwsh` and allowlists.** The dump guard and the binary allowlist split commands with POSIX grammar, which cmd.exe and PowerShell do not follow. So when the effective shell (after resolving `auto`) is cmd or pwsh and any injected secret has a non-empty `binaries` list, `exec` only accepts a single simple command: one containing none of the characters that shell can use to chain, start or substitute commands (cmd: `& | < > ^ % ! ( ) "` and line breaks; pwsh: `; & | < > ` + "`" + ` $ ( ) { } @ " '` and line breaks), whose first word, wrappers not resolved, is in every list. Anything else is refused with `scope_binary`. PowerShell's `-Command` is recognised by `-c` and every longer prefix of it (`-co`, `-com`, …, in any case and with `/` or a typographic dash), so the script after it is inspected; `-ConfigurationName` and `-CustomPipeName` are other options. In those two shells the dump guard also tests the raw command, split at every separator and ignoring quotes, so it can refuse more than under `sh`/`bash`.
- **Exit code:** the child's. On POSIX a child killed by a signal exits `128+signal` (137 for SIGKILL); on Windows the code is whatever the OS reports. Refusals exit 3 with the typed refusal on stdout (`--json`) or stderr.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | Success (for `exec`: child exited 0) |
| 1 | Generic failure; `doctor` with any `warn` or `fail` check |
| 2 | Usage error. A mistyped flag or a bad flag value ends with `; see 'qbit-vault <command> --help'` |
| 3 | Typed refusal (see CONTRACT.md) |
| 4 | Vault locked |
| 5 | Vault corrupt / rollback detected (also `remote_rollback`) |
| N | `exec`: child's exit code when > 5 is ambiguous; `--json` always carries the real `exit_code` |

Typed refusals (exit 3, 4, 5) print the contract envelope `{"ok":false,"refusal":{"type":…,"name":…,"message":…,"retryable":…}}` on stdout with `--json`, and `error: <message>` on stderr otherwise. Operating on a home with no vault is not a refusal: it exits 1 with code `not_initialized` and message `no vault here; run 'qbit-vault init'`. A vault held by another process is the refusal `internal` with `retryable: true` and message `vault is busy` (until the contract has a dedicated type).

Failures that are not typed refusals (usage errors, `not_initialized`, internal errors, panics) never print free-form output in `--json` mode: stdout carries exactly one object `{"ok":false,"error":{"code":"usage"|"not_initialized"|"cancelled"|"internal","message":"…"}}` and nothing else. Without `--json`, stderr gets `error: <message>` (usage errors add `Run 'qbit-vault --help' for usage.`). A usage error includes an invalid `--session` (must match `^[a-z0-9-]+:[A-Za-z0-9._-]{4,128}$`) and running with `--json` but no command. `--help` is always human text with exit 0. The code `cancelled` (exit 1, message `cancelled`, or `No answer in time; nothing was saved.` after the prompt timeout) is a user who gave up at a prompt: Ctrl-C, end of input, a no to a confirmation, or no answer in time; nothing was changed. Panics print only `internal error`, never the panic value.

| `QBIT_VAULT_SESSION` | Default `--session` |
| `QBIT_VAULT_PROMPT` | Force a prompt backend: `tty`, `powershell` (Windows), `osascript` (macOS), `zenity` or `kdialog` (Linux). Unset, the platform's native dialog is used when a desktop session is available (Windows: an interactive session and `powershell.exe` at its system location; macOS: `/usr/bin/osascript`, not over SSH without a GUI app; Linux: `DISPLAY` or `WAYLAND_DISPLAY` and `zenity` or `kdialog`; under **WSL** (`WSL_DISTRO_NAME` set, or `/proc/sys/fs/binfmt_misc/WSLInterop` present) the Windows dialog through `/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe`, chosen before `zenity` and `kdialog` whether or not `DISPLAY` is set, when that file exists), else the terminal. `tty` keeps the terminal for users who prefer it, which re-opens THREAT_MODEL R9 for them. A named backend that is not installed fails with the usage error `prompt backend <name> is unavailable: <program> not found …` (`powershell.exe` and `osascript` are never taken from `PATH`), never a fall back; any other value is a usage error naming the variable. |
| `QBIT_VAULT_PROMPT_TIMEOUT` | How long a prompt (terminal or native dialog) waits for an answer, a Go duration from `10s` to `1h` (default `5m`); anything else is a usage error naming the variable. On expiry the terminal is restored and the command fails with `No answer in time; nothing was saved.` (exit 1, JSON code `cancelled`), leaving everything unchanged. It covers the whole prompt (all its questions). |
| `QBIT_VAULT_RELEASES_API` | `update` (and the installers): the URL of the release to read, one release object or a list of releases (default: the `releases/latest` endpoint of `qbitdevz/qbit-vault`). `https://` only, or `http://` for a loopback host |
| `QBIT_VAULT_NO_PROMPT_UNLOCK=1` | Agent calls (MCP, host transport) that find a passphrase vault locked answer `vault_locked` instead of opening the passphrase dialog; `unlock` and every other command you run keep prompting |
| `QBIT_VAULT_NO_SYNC=1` | `update` (like the installers) does not run `sync` after replacing the binary |
| `QBIT_VAULT_NO_UPDATE_CHECK=1` | The TUI does not check for a newer release when it opens (the Update section offers `c check now`). It never affects `qbit-vault update` |
| `QBIT_VAULT_NO_REMOTE=1` | Skip every remote call for this process; changes are marked pending and `audit --verify` skips the anchors |
| `QBIT_VAULT_NO_TUI=1` | Stop `qbit-vault` with no arguments from opening the TUI (it prints the help). `qbit-vault tui` still opens it. |
| `NO_COLOR` | Honored |
